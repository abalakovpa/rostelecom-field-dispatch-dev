# Полный сценарный прогон

Работа выполняется в копии `dispatcher-next-2026-11-14` и её отдельной
PostgreSQL. Исходный проект и база `dispatcher` не используются для записи.

## Повторение

Запустите приложение копии на 8083 (`.\scripts\start.ps1`), затем из её корня:

```powershell
.\.venv\Scripts\python.exe scripts/check_scenario_api.py
```

Команда **заменяет справочники, дни, планы и события в базе копии**.
Есть защита имени проекта и базы: тест отказывается работать вне этой копии
и с базой без префикса `dispatcher_next`. Сервер ожидается только на
`127.0.0.1:8083`. Его подключение должно совпадать с локальным `.env`.

## Содержание прогона

1. Загрузка справочников и матрицы реальными HTTP PUT-запросами.
2. Загрузка и первоначальный расчёт всех 10 дней (3500 исходных нарядов).
3. События из неизменённого `events_example.json` для 12 октября.
4. Условные триггеры разворачиваются по актуальному маршруту: идентификатор
   сотрудника, время срабатывания и окончание визита берутся из текущего плана.
   После каждого события триггеры пересчитываются. Несработавший триггер
   фиксируется в отчёте с причиной, а не считается выполненной проверкой.
5. Отдельная последовательность для 13 октября гарантирует проверки задержки
   активного визита, досрочной передачи в стационар, отмены, нового наряда,
   хода времени и временной недоступности перед началом смены.
6. Повтор события, конфликтующий `event_id`, событие из прошлого и неизвестный
   наряд проверяются отдельно. Для отклонённых запросов сравнивается полное
   состояние дня, журнал, наряды и сохранённые планы до и после запроса.

Каждая версия проверяется по исходной схеме `Plan` и отдельному воспроизведению
маршрутов (`planner/validate.py`): допуски, смены, обед, слоты, длительности,
дорога, оборудование, СЦ, учёт нарядов и сохранение начатых остановок.
Дополнительно проверяются формат `EventResult`, последовательность версий,
неизменность сохранённой истории, модельное время и даты старых предупреждений.
Системные часы используются только для имени папки отчёта и измерения длительности.

Измеряется полное время HTTP-запроса. Проверяются лимиты 60 секунд на справочники
и матрицу, 30 на загрузку дня и чтение плана, 300 на первоначальный расчёт и
10 на событие. Для функционального прогона расчёт ограничен 5 секундами;
при необходимости задайте `--plan-limit 30` (допустимо 1–300).
Количество назначений при таком лимите не является итоговой оценкой оптимизации.

## Найденные и исправленные ошибки

- До начала смены временная недоступность пересекалась с новым `DEPOT_START`.
  Теперь ещё не начатый маршрут стартует после окончания недоступности;
  начатые остановки остаются неизменными. Добавлен регрессионный тест.
- Для неизвестного сотрудника, наряда или противоречащих справочникам атрибутов
  нового наряда возвращался 400. Теперь семантические ошибки дают 422,
  как предусмотрено OpenAPI. Нарушения схемы тела запроса дают 400.

Правило обеда выбывшего сотрудника не менялось. Если пример попадает в известное
противоречие, тест ожидает только 409 `UNAVAILABILITY_BREAK_CONFLICT` и отдельно
проверяет отсутствие изменений. Итог получает статус
`passed_with_known_limitation`, а не безусловный `passed`.
Вопрос остаётся отложенным, см. `open_questions.md`.

## Результаты

В `data/qa/<время-прогона>/` сохраняются `report.md`, подробный `report.json`
и JSON каждого проверенного плана. Путь к последнему завершённому прогону —
`data/qa/latest.json`. После прогона в базе копии остаются рассчитанные планы
и принятые события; первый день может показывать конец модельного дня.

Проверка исходных файлов использует контрольные суммы из `docs/copy_origin.json`.
Docker-старт и скрытый валидатор организаторов этим прогоном не проверяются.
