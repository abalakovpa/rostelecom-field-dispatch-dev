# События и перепланирование

Реализован `POST /api/v1/days/{date}/events` по исходным схемам Event/EventResult.
Поддержаны NEW_ORDER, ORDER_CANCELLED, VISIT_DELAYED, ORDER_TRANSFERRED,
STAFF_UNAVAILABLE, TIME_TICK. Требуется существующий первоначальный план.

События проверяются по оригинальному `api_spec.yaml`, время модели меняется только
при принятии события. Новый event_id должен иметь timestamp не раньше текущего
now. Одинаковый timestamp разрешён. Повтор event_id с тем же телом возвращает
сохранённый результат с duplicate=true и не увеличивает версию. Другое тело с тем
же event_id — 409. Исторические версии планов не перезаписываются.

В PostgreSQL блокируется строка дня. Событие, новый наряд при его поступлении,
обновлённое состояние и новая версия плана сохраняются одной транзакцией.
Ошибка проверки/расчёта/сохранения откатывает всё. Текущий input_snapshot содержит
рабочее состояние: модельное время, все известные наряды, интервалы недоступности
и разрешённые событиями окончания визитов. Журнал хранит исходные тела событий.
Обучающий fact в планировщик не передаётся.

Планировщик фиксирует остановки start < timestamp. Менять их сотрудника, наряд,
место, arrival/start запрещено; end меняется лишь у целевого визита по DELAYED или
TRANSFERRED. Эти события принимаются только для текущего выполняемого визита;
равенство start=timestamp допускается по схеме события. Новое продолжение не
начинает переезд раньше max(end предшественника, timestamp).

Отмена начатого визита не убирает его из маршрута. Не начатый визит исключается
и попадает в cancelled. При недоступности до until новые остановки в этом
интервале запрещены; продолжение начинается с возврата/пополнения в своём СЦ
не раньше until. Начатые визиты сохраняются. Если совместить замороженную часть,
обед и возврат не удаётся, событие отклоняется с 409, состояние не портится.

**Известное противоречие H3 и STAFF_UNAVAILABLE:** выбывшему до конца смены нельзя
добавить обязательный обед. По решению пользователя остаётся строгий режим с
409 UNAVAILABILITY_BREAK_CONFLICT; вопрос нужно напомнить при финальной сверке.
См. `open_questions.md`. Этот случай требует ответа организаторов.

Перестраивается только не начатая часть. Сначала сохраняются допустимые прежние
назначения, затем ограниченный по времени поиск вставок перераспределяет снятые
и новые наряды. Бюджет поиска 6 секунд оставляет запас до лимита 10 секунд на
проверку и транзакцию; гарантия на скрытом наборе ещё не подтверждена.
PGP пересчитывается по входным регистрациям без fact; старые группы/время
обнаружения сохраняются. Новые группы создают PGP_DETECTED. До перепланирования
прогнозируется оставшаяся очередь: LATE_RISK создаётся при прогнозе позднее
latest_start. Добавлены своевременность, проверка замены и предлагаемых слотов,
сохранение истории; см. `risks.md`. Неизвестные будущие события не предсказываются.
Качество поиска не является глобальным оптимумом.

На карте раскрывается блок «События и перепланирование»: выбор типа создаёт
редактируемый JSON-пример. Перед применением проверьте время, наряд и исполнителя.
Применение меняет состояние выбранного дня; первоначальный расчёт после этого
блокируется по спецификации. Повторить доставку можно тем же event_id/JSON через
API. Список, номера версий и маршруты обновляются после принятия события.

Проверки: `tests/test_events.py`. Дополнительная проверка реальной транзакции
PostgreSQL — `scripts/check_events_database.py`; она вставляет тестовые события
и новый наряд внутри одной изолированной транзакции, затем откатывает изменения
и проверяет неизменность исходного плана и журнала.
