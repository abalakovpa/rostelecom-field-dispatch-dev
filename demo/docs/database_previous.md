# Схема базы данных

Источник форматов — `../api_spec.yaml`. Имена полей API нельзя менять под удобство
таблиц: вложенные объекты собирает и разбирает API. Это первая реализация слоя
хранения, а не готовый сервер или модуль планирования.

## Таблицы и назначение

| Таблица в `dispatch` | Что хранит |
|---|---|
| `service_centers` | СЦ, координаты, часы работы, норматив пополнения |
| `staff` | Сотрудник, массивы профилей/технологий, допуск, смена, обед, стартовый запас и ёмкость |
| `buildings` | Уникальные дома с координатами, типом и признаком ВЛС |
| `access_nodes` | Узлы доступа и технологии |
| `access_node_buildings` | Связь многие-ко-многим: один дом может входить в разные узлы |
| `work_types` | Нормативы работ, профили, правила срока и признак участия в ПГП |
| `travel_matrices` | Идентификатор и полный JSON матрицы, включая порядок точек |
| `planning_days` | Модельное время, выбранная матрица, снимки справочников и начального ввода |
| `absent_staff` | Сотрудники, отсутствующие в конкретный день |
| `orders` | Рабочие наряды дня, окна и сроки, оборудование и связи со справочниками |
| `training_orders` | Исходные обучающие наряды с `fact`, отдельно от рабочего входа |
| `events` | Принятые события и сохранённые ответы для повторной доставки |
| `plans` | Все версии ответа `Plan` целиком, включая маршруты, ПГП и предупреждения |
| `schema_migrations` | Номер применённой миграции |
| `current_plans` (view) | Последняя сохранённая версия плана для каждого дня |

Все идентификаторы предметной области — `text`, как в API. Ключи наряда и события
составные: `(date, order_id)` и `(date, event_id)`. План: `(date, plan_version)`.
Время событий, нарядов и планов — `timestamptz`; смена и часы СЦ — местное `time`.
При выдаче API время форматируется с явным смещением, рекомендуем `+05:00`.
Исходное написание смещения `timestamptz` не сохраняет.

## Отображение вложенных объектов

| JSON API | БД |
|---|---|
| `ServiceCenter.opening_hours.open/close` | `service_centers.opening_open/opening_close` |
| `Staff.shift.start/end` | `staff.shift_start/shift_end` |
| `Staff.shift.break_duration_min` | `staff.break_duration_min` |
| `Staff.shift.break_window.from/to` | `staff.break_window_from/break_window_to` |
| `AccessNode.buildings[]` | `buildings` + `access_node_buildings` |
| `Order.slot.start/end` | `orders.slot_start/slot_end` |
| `Order.required_equipment` | JSONB-домен с ровно `ONT`, `ROUTER`, `STB` |
| `DayInput.now` | `planning_days.model_now` |
| `DayInput.absent_staff_ids` | `absent_staff` |
| `Plan`, `TravelMatrix` | `plans.payload`, `travel_matrices.payload` |

Столбцы, допускающие SQL NULL, соответствуют необязательным/nullable значениям,
за исключением служебных снимков и внутреннего ключа даты. Для точных обязательных
полей и допустимых значений смотрите OpenAPI и SQL. `previous_order_id` намеренно
без внешнего ключа: предыдущего наряда может не быть во входном наборе.

## Принятые решения

Справочники и наряды нормализованы для фильтрации и выявления ПГП. План хранится
снимком JSONB, чтобы выдавать исходный контракт, сохранять замороженную часть и
историю предупреждений без рассинхронизации нескольких таблиц. Маршруты,
остановки и назначения не дублируются отдельными изменяемыми сущностями.
Чтение актуального плана:

```sql
SELECT payload FROM dispatch.current_plans WHERE date = DATE '2026-10-26';
```

Матрица также хранится одним JSONB. API загружает её один раз и передаёт в память
планировщика; SQL-запрос на каждую пару точек не нужен. Идентификатор матрицы после
использования нельзя переопределять другим содержимым. Геометрию дорог OSRM можно
добавить отдельным кэшем позднее: она не заменяет матрицу оценки.

В исходной схеме нет ограничения общего склада СЦ: API задаёт ёмкость рюкзака и
норматив пополнения, но не конечный складской запас. Такой лимит не вводим.

## Обязательная логика API при импорте

1. Валидировать JSON/CSV по схемам OpenAPI, включая уникальность массивов,
   наличие обязательных полей, типы и непустые справочники.
2. Загружать справочники одной транзакцией: СЦ, сотрудники, дома, узлы, связи,
   типы работ. Повтор дома в разных узлах допустим только с одинаковыми атрибутами.
3. Проверять матрицу: уникальные точки; все СЦ и дома присутствуют; обе таблицы
   размера N×N; целые неотрицательные значения; нулевая диагональ. Не симметризовать.
4. Для дня проверить `date`, `now`, принадлежность слотов дню, `registered_at <= now`
   у начальных нарядов, ссылки и согласованность атрибутов дома/узла/технологии.
5. `fact` хранить только в `training_orders`; перед планированием исключать его.
   Не использовать эталонные исходы и `pgp_incident_id` как признаки солвера.
6. Сохранить снимки `ReferenceData` и `DayInput` вместе с днём. До реализации
   версионирования справочников не заменять их, пока обрабатывается активный день.

Схема намеренно не ограничивает смены условием `start < end`: правила перехода
через полночь должны быть согласованы в импортёре. Для кейса генерируем дневные
смены 09:00–18:00 и 12:00–21:00.

## Событие и перепланирование: одна транзакция

1. Заблокировать строку дня через `SELECT ... FOR UPDATE`. Все операции изменения
   этого дня, включая первоначальный расчёт, должны брать ту же блокировку.
2. Проверить `(date,event_id)`. При повторе не менять состояние и версию: вернуть
   сохранённый результат с `duplicate=true`; конфликтующее содержимое отклонить.
3. Проверить, что `timestamp` не меньше `model_now`. События с одинаковым временем
   допустимы. Вычислить новое состояние и план; не обращаться к системным часам.
4. Проверить результат по OpenAPI и H1–H10, учёт каждого наряда ровно один раз,
   сохранение начатых остановок и всех старых предупреждений.
5. Вставить событие с окончательным `result`, затем новую версию `plans`, обновить
   `model_now` и зафиксировать транзакцию. При ошибке откатить всё.

Первая версия — 1, каждое новое принятое событие добавляет 1. Ограничения БД
гарантируют уникальность номера/события и существование связей, но не проверяют
непрерывность версий и не делают снимки неизменяемыми. Запрет изменения старых
планов, проверка H1–H10 и идемпотентность целиком — обязанности будущего API.
Не выдавать приложению произвольный SQL-доступ из пользовательского интерфейса.

## Проверки и границы готовности

SQL содержит первичные и внешние ключи, проверки кодов, координат, оборудования,
границ слота и ссылок наряда. Это не полная валидация вложенных JSONB.
Миграция и импорт 3500 нарядов выполнены на PostgreSQL 18.6 в PGlite. Проверены
количества записей, откат повторного импорта, ограничения оборудования,
внешний ключ и отсутствие `fact` во входе планировщика. Отчёт находится в
`../data/database_validation_report.json`. Это не проверка Docker/PostgreSQL 17
или конкурентной доставки событий: их проверяем при подключении будущего API.

Справочные источники PostgreSQL:
[типы времени](https://www.postgresql.org/docs/17/datatype-datetime.html),
[ограничения](https://www.postgresql.org/docs/17/ddl-constraints.html).
