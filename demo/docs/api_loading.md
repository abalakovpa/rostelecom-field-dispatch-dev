# Загрузка данных через API

Рабочая копия: `dispatcher-next-2026-11-14`. Исходный проект находится уровнем
выше и не используется для записи. Для копии создана отдельная локальная база
`dispatcher_next_20261114` и отдельный пользователь с правами только на неё.
Настройки и пароль находятся в её собственном `.env`.

## Запуск копии

В PowerShell:

```powershell
Set-Location -LiteralPath 'D:\институт\3_курс\хакатон\dispatcher-next-2026-11-14'
.\scripts\start.ps1
```

Открыть <http://127.0.0.1:8083>. Python-окружение уже подготовлено в `.venv`.
Прежнее приложение на порту 8082 и его база `dispatcher` работают отдельно.
Для деморежима: `.\scripts\start.ps1 -Demo`; изменения в нём живут только в памяти.

## Контракт и последовательность

Исходный `api_spec.yaml` сохранён без изменений. Проверки используют его схемы.

| Метод | Результат |
|---|---|
| `PUT /api/v1/reference` | Полная замена СЦ, сотрудников, узлов/домов и типов работ; удаление всех дней, планов, событий и обучающих записей |
| `PUT /api/v1/reference/travel-matrix` | Загрузка квадратной неотрицательной матрицы с нулевой диагональю; проверка покрытия СЦ и домов |
| `PUT /api/v1/days/{date}` | Загрузка нарядов и отсутствующих сотрудников; повторная загрузка удаляет планы/события только этого дня |
| `POST /api/v1/days/{date}/plan` | Построение версии 1 |
| `POST /api/v1/days/{date}/events` | Событие и следующая версия плана |
| `GET /api/v1/days/{date}/plan` | Последняя версия |

Матрицу можно отправить до справочников. Если после замены справочников прежняя
матрица не покрывает новые точки, её нужно загрузить заново перед загрузкой дня.
Количество объектов не зафиксировано на нашем демонстрационном наборе.

Ответ загрузки: `{"status":"loaded","counts":{...}}`. Некорректный JSON или схема
дают 400; отсутствующие предпосылки дня — 409; противоречащие друг другу данные —
422. Ошибки возвращаются в `error.code` и `error.message`.
Неизвестные поля игнорируются; `fact` полностью исключается из рабочего входа.
Время принимается с любым корректным смещением и приводится к UTC+5. Текущее
модельное время берётся из `now` и событий.

Каждая загрузка PostgreSQL выполняется в одной транзакции. При ошибке нет
частичного удаления или импорта. Общая advisory-блокировка не позволяет
загружать данные во время расчёта/обработки события и наоборот; занятый запрос
отклоняется, его можно повторить. Другие дни сохраняются при замене одного дня.

Для уже загруженного дня сохраняется снимок матрицы. Повторный PUT матрицы
используется новыми загрузками дней; прежние планы продолжают ссылаться на
прежнюю матрицу, в том числе при повторном использовании `matrix_id`. Чтобы
перевести день на новую матрицу, повторно загрузите день и постройте план.

## Загрузка локального набора

Команда ниже **удаляет текущие дни и планы в целевом приложении**, после чего
загружает 5 СЦ, 40 сотрудников, 80 домов, матрицу 85×85 и 3500 нарядов за 10 дней:

```powershell
.\.venv\Scripts\python.exe scripts/load_case_api.py --url http://127.0.0.1:8083
```

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
node --test tests/dispatch-model.test.mjs
```

Проверки с настоящей PostgreSQL запускаются отдельно: они заменяют данные
в базе из `.env` и разрешены тестами только для имени с префиксом `dispatcher_next`:

```powershell
$env:RUN_POSTGRES_LOAD_TESTS='1'
.\.venv\Scripts\python.exe -m pytest -q
Remove-Item Env:RUN_POSTGRES_LOAD_TESTS
```

После них повторно загрузите локальный набор командой выше.
Проверены план → событие → замена дня, удаление старого журнала, сохранение
другого дня, замена справочников, откат после искусственного сбоя записи,
блокировка конкурентной загрузки, снимки матриц, неизвестные поля и смещения.

## Docker и миграции

На пустом томе Compose применяет `001_initial.sql` и `002_dataset_state.sql`.
У существующей отдельной базы с миграцией 001 нужно однократно применить 002.
К исходной базе `dispatcher` миграция в рамках этой работы не применялась.

Compose копии имеет отдельное имя `rostelecom-dispatch-next` и собственный том.
Снаружи API доступен на 8083, контейнерная база — на 5434; последний порт
настраивается через `DOCKER_POSTGRES_PORT`, независимо от `POSTGRES_PORT`
локального подключения. Внутри Docker API слушает предусмотренный кейсом 8080.
Контейнерная база изначально пустая; данные загружаются теми же PUT-методами.
Docker-сборка в этом этапе не проверялась; транзакционные проверки выполнены
на локальном PostgreSQL 18.
