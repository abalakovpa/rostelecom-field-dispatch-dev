# Синтетические данные для кейса

Это самостоятельно сгенерированный набор разработки по кейсу и исходной
OpenAPI 1.0.0. Он не является скрытым набором организаторов и не заменяет его.

| Файл | Содержимое |
|---|---|
| `service_centers.json` | 5 СЦ |
| `staff.json` | 40 сотрудников: 28 LTP3 и 12 INSTALL |
| `access_nodes.json` | 20 узлов доступа и 80 домов |
| `work_types.csv` | Все 8 типов работ и нормативы из таблицы кейса |
| `orders_train.json` | 3500 нарядов, по 350 на каждый из 10 рабочих дней |
| `events_example.json` | Сценарий первого дня: 9 событий и 3 триггера |
| `travel_matrix.json` | Направленная матрица 85×85 по дорожной сети OSRM |

`../api_spec.yaml` — ещё один обязательный файл из PDF; оригинал сохранён.
Матрица дополнительно требуется самой OpenAPI-спецификацией.

## Где требования, а где решения генератора

Кейс задаёт 5 СЦ, 40 сотрудников (28/12), смены 09–18/12–21, часовой обед,
примерно 3500 нарядов за 10 рабочих дней, нормативы, технологии и оборудование.
OpenAPI задаёт точные поля, enum, структуры, правила `latest_start`, событий и ПГП.

Выбор дат **12–23 октября 2026**, 20 узлов, 80 домов, распределение технологий,
навыков и запасов, доля повторов и конкретные события — параметры нашего
синтетического набора. Эти значения не приписываются организаторам.
Адреса, типы и контуры зданий взяты из OpenStreetMap только в Орджоникидзевском
районе Екатеринбурга (relation 5819002). Точки вычислены внутри контуров, а не
случайными смещениями или центрами ограничивающих прямоугольников. Для каждой
точки сохранены ID OSM, адресные теги и исходный контур в `provenance/real_locations.json`.
Проверяется также попадание в границу района. СЦ, сотрудники, абоненты, узлы связи,
технологии, ВЛС и наряды остаются синтетическими: реальный адрес не означает,
что там расположен настоящий СЦ Ростелекома или подключена указанная технология.
Геоданные получены через прямой API OSM; публичные Overpass-серверы не ответили.
Для синтетических повторов считаем один условный абонентский аккаунт на дом и
технологию; каждый повтор ссылается на ранее закрытый наряд в пределах 7 дней.

## Дорожная матрица

Взята из публичного OSRM Table API по OpenStreetMap, а не из расстояния по прямой.
Для каждой поездки между разными точками добавлены условные **180 секунд** на
парковку и подход; сама диагональ равна 0. Секунды и метры округлены вверх.
Это параметр генератора, а не норматив кейса. Часовые коэффициенты не применяются.
Максимальное расстояние привязки координаты к дороге записано в `manifest.json`.
Если предоставят официальную матрицу для оценки, использовать нужно её.

Публичный ответ закэширован в `provenance/osrm_table.json`; исходная матрица и
хэши координат сохранены. Благодаря кэшу повторная генерация не требует сети.
Первичное получение выполнено через документированный HTTP endpoint публичного
OSRM: HTTPS на момент подготовки возвращал ошибку срока сертификата. Личных
данных в запросе нет. Источник OSM: © OpenStreetMap contributors, ODbL,
https://www.openstreetmap.org/copyright . Документация OSRM Table:
https://project-osrm.org/docs/v5.24.0/api/#table-service .

## История и события

`fact` — синтетическая история, полученная простым последовательным назначением
с учётом навыков, смен, обеда, запасов и времени проезда. Это не результат OR-Tools.
Нормативные длительности не заменяются прогнозом. В истории есть завершённые,
перенесённые и объединённые в ПГП наряды. Разметка не должна попадать в рабочий вход
планировщика или использоваться для обнаружения ПГП.

Каждый день содержит одну исходную ПГП из трёх нарядов с одного узла за 30 минут.
Случайные регистрации остальных релевантных нарядов разнесены более чем на час,
чтобы не создать неразмеченные группы из трёх обращений. Эталонные группы отдельно
в `provenance/incidents.json`, их не передают в API планировщика.

Сценарий первого дня добавляет ещё три наряда на одном узле за 40 минут,
отменяет будущий визит и задаёт временную/до конца смены недоступность сотрудников.
Задержка и передача в подразделение заданы триггерами: оркестратор должен получить
реального исполнителя и время из текущего плана, а не угадывать их заранее.
Если соответствующего визита нет в плане, триггер пропускается по спецификации.
Не отправляйте весь файл сценария одним POST-запросом.

## Проверка и повторная генерация

Из корня проекта:

```powershell
python -m pip install -r requirements-data.txt
python scripts/generate_data.py
python scripts/validate_data.py
python scripts/build_seed_sql.py
```

Генератор использует фиксированный seed `20261113` и сохранённый дорожный ответ.
`--fetch-osrm` запрашивает обновлённые дорожные данные и может изменить матрицу;
обычно этот флаг не нужен. Генерация перезаписывает файлы набора, поэтому перед
ручными экспериментами сохраните копию. `validation_report.json` — результат
проверок OpenAPI, нормативов, ссылок, окон, сроков, повторов, ПГП и контрольных сумм.
Проверка не оценивает качество солвера и работоспособность API.

## Загрузка в pgAdmin

JSON/CSV храним как исходные файлы. Для удобного импорта есть SQL-экспорт:

1. В пустой базе выполнить `../db/migrations/001_initial.sql`, если ещё не выполнен.
2. В Query Tool той же базы открыть `../db/seeds/001_generated_data.sql` и нажать F5.
3. Обновить `Schemas → dispatch → Tables`.

Экспорт выполняется одной транзакцией, не перезаписывает существующие данные и
отклоняет повторное применение к заполненной базе. Он загружает справочники,
матрицу, обучающую историю и рабочие входы 10 дней; `fact` хранится отдельно.
Планы и события не считаются выполненными: их должен обработать будущий API.
Миграция и весь SQL-экспорт проверены на PostgreSQL 18.6 через PGlite: записи
загружены, повторный импорт отклонён, ограничения оборудования и внешнего ключа
проверены. Отчёт — `database_validation_report.json`. Ваша установка PostgreSQL
и подключение через pgAdmin этой проверкой не затрагивались.

Повторить дополнительную SQL-проверку без Docker можно так (нужен Node.js):

```powershell
npm install --prefix tmp/pg-check --ignore-scripts --no-audit --no-fund @electric-sql/pglite@0.5.16
node scripts/check_database.mjs
```
