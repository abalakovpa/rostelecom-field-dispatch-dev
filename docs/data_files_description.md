# Входные файлы: состав и значения полей

Источник точных типов, обязательности и enum — `../api_spec.yaml`, раздел
`components.schemas`. Заполненные файлы находятся в `../data/`; результаты проверок
в `../data/validation_report.json`. Контракты из прежней переписки заменены именами из OpenAPI.
JSON — UTF-8; ID — строки. Моменты времени — ISO 8601 со смещением, местное
время справочников — `HH:MM`. Координаты — отдельные `lat`, `lon`.

## 1. service_centers.json

Массив `ServiceCenter`, целевой масштаб кейса — 5 СЦ.

| Поле | Тип и смысл |
|---|---|
| `service_center_id` | Строка `SC-01`, уникальный ключ |
| `name`, `address` | Строки: название и адрес |
| `lat`, `lon` | Числа: широта и долгота |
| `opening_hours.open`, `.close` | Местное время доступности пополнения |
| `restock_duration_min` | Целое ≥ 0, длительность пополнения |

Общего складского остатка в контракте нет. Сотрудник может пополняться в другом
СЦ, но начинает и заканчивает маршрут в закреплённом.

## 2. staff.json

Массив `Staff`, целевой масштаб — 40 сотрудников: 28 3ЛТП и 12 инсталляторов.

| Поле | Тип и смысл |
|---|---|
| `staff_id` | Строка `ST-001`, уникальный ключ |
| `display_name` | Необязательная строка для интерфейса |
| `service_center_id` | Ссылка на СЦ |
| `profiles` | Непустой массив без повторов: `INSTALL`, `LTP3` |
| `technologies` | Непустой массив без повторов: `PON`, `FTTB`, `XDSL`, `DOCSIS` |
| `height_permit` | Boolean: допуск к высоте |
| `shift.start`, `.end` | Местное начало и конец смены |
| `shift.break_duration_min` | Длительность перерыва в минутах |
| `shift.break_window.from`, `.to` | Окно **начала** перерыва |
| `equipment_start` | Остаток на начало каждой смены |
| `equipment_capacity` | Запас после пополнения, по каждому виду ≥ начального |
| `experience_years` | Необязательное число ≥ 0, стаж для аналитики |

Оборудование — объект с тремя обязательными целыми неотрицательными полями
`ONT`, `ROUTER`, `STB`; другие ключи запрещены. Смены кейса: 09:00–18:00 или
12:00–21:00, перерыв 60 минут. Сменные запасы не переносятся между днями автоматически.

## 3. access_nodes.json

Массив `AccessNode`. Узел содержит дома; один дом может входить в несколько узлов
разных технологий с одинаковыми атрибутами дома.

| Поле узла | Тип и смысл |
|---|---|
| `access_node_id` | Строка `AN-0031`, уникальный ключ |
| `node_type` | `OLT`, `SWITCH`, `DSLAM`, `CMTS` |
| `technology` | `PON`, `FTTB`, `XDSL`, `DOCSIS` соответственно |
| `name`, `address` | Название и необязательный адрес |
| `lat`, `lon` | Координаты узла |
| `buildings` | Непустой массив объектов `Building` |

Дом: `building_id` (`B-00412`), `address`, `lat`, `lon`, `building_type`
(`MKD`/`PRIVATE`), `overhead_line` (Boolean), необязательный
`zone_service_center_id`. Зона СЦ справочная и не запрещает назначение из другого СЦ.
Дом определяет точку проезда, узел — связь для обнаружения ПГП.

## 4. work_types.csv

CSV по RFC 4180, UTF-8 без BOM, разделитель — запятая, первая строка — заголовки:

```csv
code,name,profiles,duration_min,max_start_delay_min,deadline_kind,deadline_value,repeat_deadline_value,pgp_relevant
```

| Поле | Тип и смысл |
|---|---|
| `code` | Один из 8 кодов `WorkTypeCode` |
| `name` | Название работы |
| `profiles` | Допустимые профили через `\|`, например `INSTALL\|LTP3` |
| `duration_min` | Целое ≥ 1, норматив работ |
| `max_start_delay_min` | Целое ≥ 0 или пусто/null: задержка начала от начала слота |
| `deadline_kind` | `SLOT`, `HOURS`, `WORKING_DAYS` |
| `deadline_value` | Целое ≥ 1 или пусто/null для `SLOT` |
| `repeat_deadline_value` | Срок повтора, пусто/null означает обычный срок |
| `pgp_relevant` | Boolean: участвует ли тип работы в выявлении ПГП |

Нормативы из кейса для будущего заполнения: `INST_PON_MKD` — 90,
`INST_FTTB_MKD` — 60, `INST_PRIVATE_VLS` — 180, `ADD_SERVICE` — 40,
`SURVEY_PRIVATE` — 45, `REPAIR` — 60, `DEGRADATION` — 45, `DISMANTLE` — 30 минут.
Для инсталляции ограничение старта — 10 минут. Конкретный `deadline` каждого
наряда приходит готовым; солвер не должен заново рассчитывать производственный календарь.

## 5. travel_matrix.json

Один объект `TravelMatrix`, не массив.

| Поле | Тип и смысл |
|---|---|
| `matrix_id` | Строка, версия матрицы |
| `points` | Уникальные ID всех СЦ и домов, минимум 2 точки |
| `durations_sec` | N×N целых неотрицательных значений времени в секундах |
| `distances_m` | N×N целых неотрицательных расстояний в метрах |
| `hourly_factors` | Необязательный массив `{hour, factor}`, час 0–23, коэффициент ≥ 0 |

Ячейка `[i][j]` соответствует поездке `points[i] → points[j]`. Матрица может быть
несимметричной; диагональ 0. Время включает парковку и подход к подъезду.
В базовой оценке часовые коэффициенты не применяются. OSRM можно использовать
для подготовки собственной матрицы и геометрии, но на оценке обязательна матрица
из `PUT /reference/travel-matrix`.

## 6. orders_train.json

Массив `Order`: примерно 3500 нарядов за 10 рабочих дней. День определяется
датой `slot.start` в `Asia/Yekaterinburg`.

| Поле | Тип и смысл |
|---|---|
| `order_id` | Строка `ORD-20261026-0001`, уникальный наряд |
| `work_type_code`, `technology` | Код типа работ и технология |
| `building_id`, `access_node_id` | Дом для маршрута, узел для ПГП |
| `address`, `lat`, `lon`, `building_type` | Атрибуты адреса из справочника домов |
| `requires_height` | Boolean: нужен ли допуск к высоте |
| `registered_at` | Момент регистрации |
| `slot.start`, `.end` | Согласованный двухчасовой слот |
| `latest_start` | Последний допустимый момент начала визита |
| `deadline` | Контрольный срок завершения |
| `required_equipment` | Объект `ONT/ROUTER/STB`, целые ≥ 0 |
| `is_repeat` | Boolean: повтор, повышенный вес 2 |
| `previous_order_id` | Необязательная nullable ссылка; предшественника может не быть в наборе |
| `fact` | Необязательная nullable обучающая разметка; исключается из рабочего входа |

`fact` может содержать `outcome`, `staff_id`, `actual_start`, `actual_duration_min`,
`pgp_incident_id`. Это история для аналитики, не подсказка при распределении.
При загрузке дня выбираются только наряды нужной даты с `registered_at <= now`.
Более поздние поступают через `NEW_ORDER`.

## 7. events_example.json

Объект `EventScenarioFile`: `date`, `now`, массив `events`, массив `triggers`.
Это сценарий локального оркестратора, а не готовое тело одного POST-запроса.

Каждое событие содержит `event_id`, `type`, `timestamp` и поля своего типа:

| Тип | Дополнительные поля |
|---|---|
| `NEW_ORDER` | `order` — полный новый наряд |
| `ORDER_CANCELLED` | `order_id`, `reason`: `NOT_CONFIRMED`/`CUSTOMER_REQUEST` |
| `VISIT_DELAYED` | `staff_id`, `order_id`, `expected_end` |
| `ORDER_TRANSFERRED` | `staff_id`, `order_id`, `actual_end`, `transferred_to`: `STATION_EQUIPMENT`/`TRUNK_CABLE` |
| `STAFF_UNAVAILABLE` | `staff_id`, `reason`: `VEHICLE_BREAKDOWN`/`ILLNESS`/`OTHER`; необязательное nullable `until` |
| `TIME_TICK` | Нет дополнительных полей |

События передаются по неубыванию `timestamp`, повтор `event_id` идемпотентен в
пределах дня. `until=null` означает недоступность до конца смены.

Триггер содержит `trigger_id`, `type` (`VISIT_DELAYED`/`ORDER_TRANSFERRED`),
`order_id`, `fire_after_start_min`; дополнительно `extra_duration_min` для
задержки или `transferred_to` для передачи. Оркестратор определяет сотрудника
по текущему плану и время `VISIT.start + fire_after_start_min`, затем создаёт
обычное событие. Если визита нет в маршруте, триггер пропускается.

## Порядок подготовки и загрузки

Сначала СЦ и типы работ, затем сотрудники, узлы и дома, затем матрица, наряды и
сценарии. В API справочники загружаются совместно через `PUT /reference`, матрица
отдельно через `PUT /reference/travel-matrix`, день через `PUT /days/{date}`.
`api_spec.yaml` уже присутствует и является контрактом, его не генерируем заново.
Все семь файлов данных сгенерированы. В PDF перечислены шесть из них и
`api_spec.yaml`; седьмой файл данных — матрица — обязателен по OpenAPI.
Происхождение, параметры генератора и порядок загрузки в pgAdmin описаны в
`../data/README.md`. Условные адреса и даты генерации не являются требованиями кейса.
