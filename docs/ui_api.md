# Контракт карты для Fastify — на согласование

Машиночитаемое описание: `../contracts/ui-api.yaml`. Основной `../api_spec.yaml`
не менялся и не дублируется: `Plan`, события и ошибки берутся из него через `$ref`.
Файлы в `../contracts/examples/` — JSON-примеры; список схем — `manifest.json`.
Это предложение для серверного разработчика, а не уже согласованный контракт.

## Отдача статических файлов

Fastify отдаёт `web/index.html` на `/`, каталог `web/` — на `/static/`.
API и статика находятся на одном origin: карта использует относительные URL;
при такой схеме CORS не нужен. `.js` отдаётся как JavaScript, `.css` — как CSS.
Для HTML и модулей во время интеграции отключить устаревшее кеширование.
На GET-ответах UI рекомендуем `Cache-Control: no-store`.

## 1. `GET /api/ui/bootstrap`

Тело запроса отсутствует. Ответ 200 (`UiBootstrap`):

- `data_source`: `postgres` для рабочего сервера; `demo` для локального просмотра.
- `days[]`: `date` (`YYYY-MM-DD`), `model_now` (ISO 8601 со смещением), `orders_count`.
- `service_centers[]`: `service_center_id`, `name`, `address`, `lat`, `lon`.
- `staff[]`: `staff_id`, необязательный `display_name`, `service_center_id`,
  `profiles[]`, `technologies[]`, `height_permit`, `shift_start`, `shift_end`.
  Смены — местное время `HH:MM` или `HH:MM:SS`; вложенного `shift` здесь нет.
- `work_types[]`: `code`, `name`, `duration_min`, `profiles[]`.

Дополнительные поля допустимы. Пустая база — 200 с пустыми массивами,
не переключение на синтетические данные. Дни сортируются по дате.
Примеры: `bootstrap.json`, `bootstrap-empty.json`. Ошибка БД — 503 `ErrorResponse`.

## 2. `GET /api/ui/days/{date}`

Тело запроса отсутствует. Ответ 200 (`UiDay`): `data_source`, `date`, `model_now`,
`orders[]`, `plan`. `plan` — официальный `Plan` последней версии либо **`null`**,
если день загружен, но расчёта ещё нет. Наряды выдаются и без плана.

`orders[]` содержит поля официального `Order`, кроме:

- `slot` развёрнут в `slot_start` и `slot_end` (ISO 8601);
- обучающий `fact` не передаётся в UI.

`previous_order_id` необязателен. В состав входят исходные и новые наряды;
отменённые остаются в `orders`, их статус берётся из `plan.cancelled`.
Вложенный `plan` сохраняет исходный формат организаторов: `routes`, `stops`,
`unassigned`, `pgp_groups`, `cancelled`, `alerts`. Никакого преобразования его
в формат прототипа не требуется. `summary` необязателен: UI считает сводку сам.
Необязательные поля прогноза показываются только при их наличии.

Fastify должен прочитать `model_now`, наряды и последнюю версию плана как один
согласованный снимок, чтобы событие посреди чтения не смешало разные версии.
Предлагаем порядок нарядов: `slot_start`, затем `order_id`.
Примеры: `day-planned.json`, `day-unplanned.json`, `day-empty.json`.

Ошибки: 400 — некорректная дата; 404 `DAY_NOT_LOADED` — дня нет;
503 — недоступно хранилище. Отсутствие плана — 200 с `plan:null`.

## 3. `GET /api/ui/days/{date}/routes/{staff_id}/geometry`

Тело запроса отсутствует. Ответ 200 (`UiRouteGeometry`):

- `staff_id`, `plan_version` — версия, для которой рассчитана геометрия;
- `geometry` — GeoJSON `LineString` всего маршрута;
- `segments[]`: `from_stop`, `to_stop`, `geometry` (GeoJSON `LineString`).

GeoJSON и маркеры MapLibre GL JS используют **`[lon, lat]`**.
Сегменты идут по направлению движения. Подписи визитов — `"1"`, `"2"` и т.д.,
СЦ — `"СЦ"`. Визиты нумеруются по `VISIT`, без учёта обеда и пополнения.
Последовательные одинаковые `location_id` не образуют дорожный сегмент:
перерыв на месте и несколько визитов в одном доме не создают лишнюю линию.
При пустом маршруте разрешены пустые `coordinates`/`segments`.

Геометрия — только для показа. Время и допустимость назначений определяются
официальной матрицей. Прямую линию между адресами нельзя подставлять вместо
недоступного дорожного маршрута. Конкретный поставщик геометрии — решение сервера;
демо использует OSRM. Лимит запроса карты пока не согласован с серверным разработчиком.

Карта проверяет `plan_version` и `staff_id`: несовпавший ответ не рисуется,
диспетчер получает предложение обновить данные. Пример `route-geometry.json`
показывает **структуру**, его координаты схематичны и не являются дорожным маршрутом.
Пример ошибки: `geometry-unavailable.json`.

Ошибки: 400 — параметры; 404 — нет дня, плана или сотрудника;
502 `ROUTING_UNAVAILABLE` — недоступна дорожная геометрия; 503 — хранилище.
Ошибка геометрии не меняет план; список и Гант остаются доступны.

## Что карта вызывает в основном API

| Метод | Запрос | Ответ |
|---|---|---|
| `POST /api/v1/days/{date}/plan` | `{"time_limit_sec":30}` | Официальный `Plan` |
| `POST /api/v1/days/{date}/events` | Официальный `Event` | Официальный `EventResult` |

После успешной записи карта заново читает `/api/ui/days/{date}`. Обработка
повторного события, модельное время и сохранение начатых визитов — ответственность
Fastify и планировщика Павла. JSON-примеры запросов и `EventResult` лежат рядом
с примерами GET. Новые записывающие `/api/ui` не добавляются.

Ошибки всех методов имеют официальный формат `{"error":{"code":"...","message":"..."}}`.
Модельное время не берётся с часов компьютера. Источник данных не влияет на формат.
Для точного показа переездов Ганта серверу желательно заполнять справочный
`stops[].travel_sec` по матрице; если его нет, UI не может выделить время дороги
из общего разрыва между остановками и не считает этот разрыв доказанной дорогой.

## Приёмка интеграции

Пустая база → загруженный день без плана → расчёт → новая версия после события
→ повтор события без новой версии → недоступная геометрия → обновлённая версия
геометрии. Затем проверить статусы, Гант, ПГП и предупреждения по одному и тому же
снимку. Совместный запуск с Fastify и планировщиком Павла ещё предстоит.

## Общие аварии и предупреждения интерфейса

`plan.pgp_groups` — официальная передача в станционное подразделение:
наряды исключены из индивидуальных маршрутов. `plan.incident_groups` —
командное расширение общей аварии с `action: INDIVIDUAL_VISITS`: эти наряды
по-прежнему учитываются ровно один раз в `routes` или `unassigned`.
Оба источника входят в фильтр и обозначения «ПГП». Для `incident_groups`
статус назначения сохраняется; карточка дополнительно показывает связь с аварией.
Поэтому счётчики «Назначены» и «ПГП» могут пересекаться.

Предупреждения берутся из `plan.alerts`. Для групп без отдельного серверного
сигнала UI строит карточку из фактического `incident_groups` / `pgp_groups`.
Эти карточки не записываются обратно в официальный Plan. Одна функция
`projectWarnings(day)` питает список и красный/зелёный индикатор. Все отменённые
или уже завершённые по модельному времени участники закрывают карточку общей
аварии; история доступна через «Показать закрытые».

Для `LATE_RISK` планировщик сохраняет UI-метаданные: `warning_deadline` —
начало первоначального слота минус 30 минут; `timely` — был ли сигнал создан
не позднее этого момента; `forecast_at` — время формирования прогноза.
При автоматическом переносе отсчёт не сдвигается на новый слот.
`forecast_start` / `lateness_min` выдаются только при наличии расчёта,
отсутствующий прогноз не означает недоступность сотрудника.
При переносе в другой день или отмене активный риск закрывается и остаётся
в истории. UI получает эти расширения через `/api/ui/days/{date}`;
исходный `api_spec.yaml` не изменён.

Полный пример ответа Fastify с тремя назначенными нарядами общей аварии:
`docs/examples/ui-day-incidents.json`. Он получен в изолированной PostgreSQL
и проверяется тестом UI-проекции; входы из основной базы не использовались.

## Кнопка расчёта и обновления плана

Кнопка расчёта использует `POST /api/v1/days/{date}/plan` только когда плана
ещё нет. Для существующего плана, в том числе после событий, «Обновить план»
сначала перечитывает актуальный день и отправляет `TIME_TICK` с новым `event_id`
и текущим `model_now` через `/events`. Это запускает штатное перепланирование,
не передвигает модельные часы и сохраняет начатую часть маршрутов.
UI блокирует кнопку только на время запроса или при отсутствии загруженного дня.

## Каталог формы создания заявок

GET /api/ui/catalog возвращает buildings[], works[], staff[] из действующего
снимка PostgreSQL. В building добавлены access_node_id и technology узла.
Панель использует этот endpoint для списка адресов и повторно читает его
при создании заявки. Файлы data/ используются только для явной загрузки
демонстрационного набора, а не как альтернативный источник адресов.
Это расширение UI API; исходный официальный api_spec.yaml не меняется.
