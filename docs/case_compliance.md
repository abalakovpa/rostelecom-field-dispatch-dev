# Сверка с кейсом и OpenAPI

Источники: `../Кейс №05 Ростелеком (про).pdf`, п. 2.2–2.3, 4–6;
`../api_spec.yaml` версии 1.0.0. Их содержимое не менялось.
Это сверка подготовленных данных и хранения, а не заявление о готовности всего решения.

## Содержимое и проверки

- Технологии: `PON`, `FTTB`, `XDSL`, `DOCSIS`; профили: `INSTALL`, `LTP3`.
- Оборудование: ровно `ONT`, `ROUTER`, `STB`, целые неотрицательные количества.
- Смены: 09:00–18:00/12:00–21:00, обед 60 минут. По OpenAPI окно обеда
  ограничивает его начало, а не весь интервал.
- Слоты: 2 часа; для инсталляции `latest_start = slot.start + 10 мин`.
  При проверке плана оценивается начало визита в соответствии с H4 OpenAPI.
- Нормативы: 90/60/180/40/45/60/45/30 минут в порядке строк таблицы кейса.
  Сроки: 3/3/5 рабочих дней, слот, 2 рабочих дня, 24/12 часов, 48 часов,
  5 рабочих дней. Готовый `deadline` записан в каждом наряде.
- Повторы ссылаются на завершённый предыдущий наряд того же синтетического
  аккаунта/услуги в пределах 7 дней после закрытия.
- ПГП: не менее 3 релевантных нарядов одного узла за 60 минут по OpenAPI.
  В обучающем наборе есть 10 таких групп и отдельно проверено отсутствие
  неразмеченных групп из трёх обращений.
- Сценарий покрывает все 6 типов событий: `NEW_ORDER`, `ORDER_CANCELLED`,
  `VISIT_DELAYED`, `ORDER_TRANSFERRED`, `STAFF_UNAVAILABLE`, `TIME_TICK`.
- Проезд рассчитан по дорожной сети. Данные матрицы сохраняют направление;
  диагональ нулевая, геометрическая оценка вместо OSRM не используется.
- Все JSON/CSV прошли валидацию по исходным схемам OpenAPI и межфайловым связям.
- SQL создания таблиц и загрузки набора выполнен во встроенном PostgreSQL;
  отчёты находятся в `data/validation_report.json` и `data/database_validation_report.json`.

Число узлов/домов, конкретные даты, выбор адресов OSM, запасы, 180 секунд
парковки/подхода и распределение видов работ — параметры синтетического
генератора, которых кейс не фиксирует. Они перечислены в `data/README.md`.
География ограничена Орджоникидзевским районом по текущему указанию пользователя;
точки проверены внутри реальных адресных зданий и границы района, см. `docs/geography.md`.
При появлении официальных входных данных сервис должен принимать их без
привязки к размерам, датам и идентификаторам нашего набора.

## Что ещё необходимо реализовать по кейсу

Готовы исходные файлы, слой хранения, SQL-импорт, каркас FastAPI и первая карта
Leaflet с СЦ/нарядами, выбором дня, поиском, фильтрами и списком сотрудников.
Добавлены health, расчёт первоначального плана через OR-Tools CP-SAT, его сохранение,
независимая проверка первоначальных маршрутов и дорожные линии OSRM с номерами визитов.
Начальная ПГП выделяется по входным нарядам без чтения `fact`. Ограничения
эвристики и результат первого живого прогона описаны в `docs/planner.md` и
`data/planner_validation_report.json`. Остальные методы контракта ещё нужны.
Добавлены обработка шести типов событий, транзакционное сохранение новых версий,
заморозка начатых остановок, обновление ПГП и предупреждения при снятии/передаче визита.
Добавлены Гант (работа/дорога/ожидание/обед/АО), загрузка сотрудников, фильтры
статусов, причины неназначения и панели сохранённых предупреждений и ПГП.
Статусы исполнения явно помечены «по плану», без утверждения фактических отметок.
Добавлены прогноз начала будущих визитов до ремонта плана, минуты опоздания,
проверка обнаружения за 30 минут до слота, проверенные замены/слоты и история
закрытия риска. Неизвестные события не предсказываются, времена не задатируются;
см. `docs/risks.md`.
Есть строго отклоняемый противоречивый сценарий обеда выбывшего сотрудника:
см. `docs/open_questions.md`; напомнить пользователю при итоговой сверке.
Пока не реализованы: полный REST API загрузки данных; глобальное улучшение маршрутов;
полный локальный оркестратор с разворачиванием зависимых от визитов триггеров;
полная оценка качества и своевременности предупреждений на всех сценариях;
измерение лимитов 300/10 секунд на всех сценариях;
оценка по скрытому набору и презентация. Наличие данных и БД эти требования
само по себе не выполняет. Compose содержит БД и API с интерфейсом; полный сценарий
оценки ещё не поддерживается. Дополнительные задания не объявляются реализованными.
