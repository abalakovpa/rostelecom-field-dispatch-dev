# Внутренний контракт сервера и планировщика

Для интеграции используем [OpenAPI 1.0.0 организаторов](https://github.com/abalakovpa/rostelecom-field-dispatch-dev/pull/5). `plan_openapi` принимает данные по этой схеме. Ниже также сохранён прежний вызов `plan(request)` и его временный синтетический пример.

## Вызов по OpenAPI

```python
from planner_openapi import plan_openapi

initial = plan_openapi(reference, matrix, day, time_limit_sec=290)
updated = plan_openapi(
    reference, matrix, current_day, previous=initial, event=event,
    cancelled=cancelled, pgp_groups=pgp_groups, time_limit_sec=8,
)
```

`reference`, `matrix` и `day` соответствуют `ReferenceData`, `TravelMatrix` и `DayInput`. Результат соответствует `Plan`. Для пересчёта `current_day.orders` содержит все наряды дня, включая принятые `NEW_ORDER` и наряды уже начатых визитов. Сервер проверяет событие, передаёт накопленные `cancelled` и `pgp_groups` и сохраняет ответ как актуальную версию. Начатый визит остаётся в маршруте и не включается в ПГП или отменённые. Эталон ПГП описан в схеме `PgpGroup`. Это не менее трёх нарядов с `pgp_relevant = true`, зарегистрированных за 60 минут на одном узле. Сервер также отвечает за HTTP-лимиты и повторные `event_id`.

В расчёте используются секунды из `durations_sec`, границы `latest_start` и `deadline` из наряда, окно начала обеда из смены и `equipment_capacity` при пополнении. При пересчёте начало до `event.timestamp` замораживает остановку. `VISIT_DELAYED` и `ORDER_TRANSFERRED` меняют её окончание по событию. При новом предшественнике время поездки отсчитывается не раньше модельного времени. Для опаздывающего визита создаётся `LATE_RISK`.

В [синтетическом примере](examples/planner-openapi.json) первый визит начинается в 09:10:01. Событие в 09:35 сдвигает окончание до 11:10. Следующий визит не помещается в слот до 11:20 с учётом пополнения. В версии 2 первый визит сохраняет время начала, второй попадает в `unassigned`, а в `alerts` появляется `LATE_RISK`. Обе версии планировщика и пример проверяются командой `python -B -m unittest discover -s tests -v`.

## Прежний внутренний вызов планировщика

Сервер хранит состояние смены, применяет события и передаёт в `plan(request)` согласованный снимок. `as_of` задаёт время снимка. На первый расчёт передаются сотрудники в закреплённых СЦ на начало их смен. При пересчёте сервер передаёт фактические позиции, остатки, время следующей доступности и выполненные операции. Состояние включает данные уже начатой работы, если она идёт на момент снимка. Планировщик рассчитывает маршрут на один день. Сервер проверяет, что версия снимка по-прежнему актуальна, перед сохранением результата. Наряды, переданные в станционное подразделение, исключаются сервером из индивидуального планирования.

| Поле запроса | Что передаёт сервер |
| --- | --- |
| `plan_date`, `as_of` | Дата смены и время снимка. Все моменты времени в формате ISO 8601 с явным смещением от UTC. |
| `workers[]` | `id`, `center_id`, `profiles`, `technologies`, `height_permit`, `shift`, `lunch`. Смена и обед заданы интервалами `start_at`, `end_at`. При первом расчёте `stock` задаёт начальные остатки по видам АО. При пересчёте берём остатки из `current_state`. |
| `centers[]` | `id`, `location_id`, `open_intervals`, `equipment_available` (остатки по видам АО) и `replenishment_minutes` (длительность заезда). Предлагаем передавать длительность параметром. |
| `orders[]` | Активные наряды с `id`, `location_id`, `work_type_id`, `technology`, `registered_at`, `slot`, `due_at`, `is_repeat`, `requires_height`, `equipment`. `requires_height` выставляется для работ в частном секторе с воздушной линией. `due_at` допускает `null` для работ со сроком только по слоту. |
| `work_types[]` | `id`, допустимые `profiles`, `duration_minutes`, `arrival_grace_minutes`. Для инсталляций допуск от начала слота равен 10 минутам. `null` означает, что действует весь слот. |
| `travel_minutes` | Матрица времени в пути. `location_ids` задаёт порядок строк и столбцов `values`. Строка соответствует отправлению, столбец прибытию. Время в целых минутах, `null` обозначает недоступный переезд. Матрица может быть несимметричной. |
| `current_state` | `null` для первого расчёта. При пересчёте сервер передаёт в `workers[]` запись для каждого сотрудника с `worker_id`, `location_id`, `available_at`, `stock` и `locked_steps[]`. `location_id` задаёт точку, в которой сотрудник будет доступен в `available_at`. `locked_steps[]` содержит выполненные шаги и текущую работу в хронологическом порядке со статусами `completed` и `in_progress`. Для текущей работы время окончания прогнозное. `available_at` учитывает её прогнозное окончание, а `stock` отражает остаток к моменту следующей доступности с учётом текущей работы. `previous_assignments[]` содержит прежние назначения с `worker_id`, `order_id`, `planned_arrival_at` для оценки рисков. |

Время `due_at` сервер рассчитывает при нормализации по типу работ и календарю. Для устранения неисправности по обращению абонента действуют 24 часа с регистрации и 12 часов при повторном обращении. Наряды с просроченным контрольным сроком участвуют в распределении. Просрочка завершения и попадание в слот проверяются отдельно.

## Результат

| Поле ответа | Что возвращает планировщик |
| --- | --- |
| `routes[]` | `worker_id` и упорядоченные `steps[]`. Типы шага: `start`, `visit`, `lunch`, `replenishment`, `return`. У каждого шага есть `location_id`, `start_at`, `end_at`, `travel_minutes` от предыдущего шага и `status` (`planned`, `completed`, `in_progress`). Визит дополнительно содержит `order_id`, `arrival_at` и `deadline_met` (`null` при отсутствии отдельного контрольного срока). У заезда на пополнение есть `equipment_added`. Для первого расчёта `start` и `return` обозначают моменты выезда из СЦ и возвращения. |
| `unassigned[]` | `order_id`, `reason_code` и при необходимости `details`. Предлагаемые коды: `NO_QUALIFIED_WORKER`, `SLOT_UNREACHABLE`, `INSUFFICIENT_STOCK`, `SHIFT_INFEASIBLE`, `ROUTE_UNREACHABLE`. При нескольких препятствиях планировщик возвращает первое по стабильному порядку проверок. |
| `risks[]` | `order_id`, `worker_id`, `estimated_arrival_at` и `reason_code` для риска в прежнем назначении. `action` содержит `type` (`reassign`, `propose_reschedule`, `manual_review`) и `worker_id` при передаче. При передаче новый визит должен удовлетворять всем ограничениям. Если до начала слота меньше 30 минут, ответ предлагает ручную обработку. Новый слот вступает в силу после согласования с абонентом. |

Каждый входной активный наряд появляется ровно один раз среди визитов и неназначенных. Риски могут относиться к любой из этих записей. При пересчёте выполненные и начатые шаги сохраняются в маршрутах. Прогноз опоздания передаётся в `risks` и не служит разрешением поставить визит за пределами слота.

Для предупреждения `SLOT_UNREACHABLE` планировщик оценивает время прибытия по прежней очереди оставшихся визитов, начиная от текущей позиции и времени доступности сотрудника. Если в новом плане визит остаётся у того же сотрудника и укладывается в слот, предупреждение не требуется. `reassign` указывает сотрудника, которому визит уже назначен в новом плане. Для оставшегося без назначения визита выбирается `propose_reschedule` при запасе от 30 минут до начала слота или `manual_review` при меньшем запасе.

## Модель и первый алгоритм

Для каждого сотрудника поддерживаем упорядоченный маршрут. Пробуем вставить очередной наряд в каждую позицию каждого подходящего маршрута и заново считаем время и остатки на изменившейся части. При необходимости пробуем вставить заезд на пополнение. Отбрасываем варианты без нужного профиля, технологии или допуска, без оборудования, с нарушением обеда, смены, слота либо возврата в закреплённый СЦ. В первой версии считаем, что переезд и работа не пересекают часовой обед. У инсталляции прибытие допустимо до `slot.start_at + 10 мин` включительно и до окончания слота. Время окончания работы может выходить за слот при соблюдении смены и обеда.

Порядок целей лексикографический. Сначала увеличиваем взвешенное число визитов в слот и завершений в контрольный срок. Для первого прогона предлагаем вес 2 для повторного обращения и 1 для остальных. Далее минимизируем число предложенных переносов, затем суммарное время в пути, затем разброс занятости сотрудников. Для воспроизводимости перебираем наряды в порядке окончания допустимого окна, контрольного срока и ID, повышая приоритет повторных обращений при равных сроках. При пересчёте применяем вставку к оставшейся части маршрутов. Жадная вставка даёт результат на небольшом примере и позволяет отдельно проверить каждое ограничение. Качество плана и пределы 5 минут на дневной расчёт и 10 секунд на ответ по событию проверим на выборке 350–450 нарядов.

## Проверка примера

Для локальной проверки запусти из корня проекта команду PowerShell:

```powershell
python -B -c "import json; from pathlib import Path; from planner import plan; data = json.loads(Path('docs/examples/planner-contract.json').read_text(encoding='utf-8')); print(json.dumps(plan(data['request']), indent=2))"
```

`plan(request)` строит дневной план и пересчитывает оставшиеся визиты по снимку смены. Для подбора маршрутов планировщик резервирует АО в пределах одного расчёта и при изменении маршрута пересчитывает резерв этого сотрудника. При пересчёте доступный запас СЦ во входных данных уже учитывает начатые и завершённые пополнения. При равных результатах по контрольным срокам и переездам планировщик сравнивает разброс занятости. В занятость входят визиты, заезды за АО и переезды.

- `I-01` начинается ровно на десятой минуте слота. У `I-03` подходящий профиль и технология есть, но нет высотного допуска. Его причина `NO_QUALIFIED_WORKER`.
- `R-01` начинается внутри слота и заканчивается на 15 минут позже контрольного срока для повторного обращения. Для него `deadline_met` равен `false`.
- Оба сотрудника соблюдают часовой обед и возвращаются в закреплённый СЦ до конца смены. Установки расходуют по одной единице указанного АО.
- Сроки инсталляций в примере считаются до конца третьего или пятого рабочего дня после регистрации, при рабочей неделе с понедельника по пятницу. Это допущение для тестовых данных.
- При снимке в 10:20 `I-01` ещё выполняется, а его окончание прогнозируется на 11:15. До `I-02` ехать 20 минут, ожидаемое прибытие в 11:35 выходит за предел 11:10. Второй сотрудник не имеет профиля инсталлятора. В результате `I-02` получает `SLOT_UNREACHABLE` и действие `propose_reschedule`.
- При снимке в 11:15 `I-01` сохраняется со статусом `completed` и фактическим окончанием в 11:15. Для `I-02` теперь требуется `manual_review`.

Оба снимка и вариант передачи подходящему сотруднику собраны в `tests/test_planner.py`. Запуск проверки из корня проекта:

```powershell
python -B -m unittest discover -s tests -v
```

## Вопросы для согласования

- С Игорем согласовать вызов Python из сервера и пройти HTTP-сценарий из OpenAPI от загрузки справочников до `GET /api/v1/days/{date}/plan` после задержки.
- Согласовать подтверждение нового слота. `deadline` для загруженных нарядов уже задан организаторами, а тестовые данные должны содержать его явно.
