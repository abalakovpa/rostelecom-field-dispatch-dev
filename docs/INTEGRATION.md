# Интеграция Fastify, карты и планировщика

Ветка integration/fastify-map-planner собрана отдельной рабочей копией.
Это выборочный перенос компонентов, а не слияние всех файлов веток:

- Fastify, миграции, Compose: feat/official-rest-api, 8b8a905.
- web/, contracts/, данные и предложение БД: feature/dispatcher-app, 3b7b7bd.
- planner.py, planner_openapi.py, тесты и примеры: codex/planner-contract, df48777.

Старый FastAPI и экспериментальный OR-Tools-планировщик в сборку не включены.
Предложенная нормализованная схема Михаила сохранена, но автоматически
не применяется: пока сервер использует api_state и согласованный runner.

## Запуск

    docker compose up --build -d --wait

Адрес по умолчанию http://127.0.0.1:8080/. PostgreSQL 16 в именованном томе.
Локальный пароль по умолчанию предназначен только для оценки. Bash-скрипт
scripts/deploy.sh генерирует собственный .env. Миграции выполняются отдельно
перед API; planner — внутренний Python HTTP-сервис, порт не публикуется.

Для отдельной проверки на ноутбуке PowerShell:

    $env:API_PORT='18081'
    $env:DB_PORT='15436'
    docker compose -p dispatcher-integrated-qa up --build -d --wait

    python scripts/check_integrated.py --url http://127.0.0.1:18081 --allow-reset

Последняя команда заменяет данные целевого API. Использовать только тестовый
экземпляр. Она загружает небольшой пример Павла: сотрудники и три наряда,
строит план, передаёт задержку, проверяет новую версию, повтор и ошибку.
После неё в UI можно выбрать 2026-10-26 и посмотреть фактический план.

## Этап: прерывание и временная недоступность

Реализовано: STAFF_UNAVAILABLE снимает текущий незавершённый визит с прежнего
исполнителя, сохраняя запись в day._interrupted_visits/Plan.interrupted_visits.
Наряд снова участвует в назначении вместе с последующими. Остаток длительности
считается как прежний прогнозный end минус timestamp события. Установленное
оборудование считаем оставшимся на объекте: оно остаётся расходом первоначального
мастера, повторного расхода на продолжение нет. Это явное допущение прототипа:
для реальных неустановленных/возвратных материалов нужна отдельная модель.

Временное выбытие: перед продолжением добавляется RESTOCK в домашнем СЦ,
не раньше until, с длительностью пополнения и заполнением до capacity.
Таким образом, until сейчас означает доступность для пополнения, а не готовность
немедленно выехать с уже пополненным комплектом. Запас не восстанавливается магически.

Отклонение от исходного H10 сделано только для прерванного текущего VISIT
при STAFF_UNAVAILABLE в соответствии с решением пользователя. Выполненные визиты
остаются замороженными. Исходный api_spec.yaml не изменён.

11 Python-тестов проходят, включая назначение остатка работы другому мастеру
и пополнение при возврате. В Docker повторно прошёл интеграционный smoke,
включая STAFF_UNAVAILABLE после задержки и выдачу истории прерывания через API.
История пока доступна в JSON, отдельное отображение её в интерфейсе не реализовано.

Если продолжение не укладывается в прежний слот, оно пока попадает в unassigned.
Автоматическое изменение слота и группа аварии с индивидуальными визитами —
следующий этап; этот коммит не объявляет их завершёнными.

## Этап: автоматические слоты и группы аварий с визитами

planner-service/policies.py — прикладной слой над алгоритмом Павла.
После события сначала пробуется прежний слот/другой исполнитель. Для
неназначенных нарядов ищется более поздний двухчасовой слот текущего дня
с шагом 30 минут, в пределах deadline. Для каждого варианта выполняется
полный расчёт ограничений; уже назначенные наряды не вытесняются.
Поиск ограничен общим бюджетом. Если варианта нет, остаётся unassigned.
Переход на другой день пока не реализован.

Python возвращает внутренние _order_updates; Fastify проверяет новые
поля по Order и временным ограничениям, атомарно сохраняет обновлённый
слот вместе с планом. Внешне _order_updates не выдаются. История старых
и новых слотов — automatic_reschedules, предупреждение applied=true.
Это автоматическое решение по уточнению пользователя для ручной проверки,
а не имитация подтверждения от абонента по прежнему контракту.

Группы с индивидуальными выездами — incident_groups (дополнительное поле).
Официальный pgp_groups остаётся отдельным, эксклюзивным способом учёта.
Группа создаётся от трёх релевантных обращений узла за 60 минут. Новые
обращения присоединяются по соседству до 60 минут хотя бы с одним из
участников; сохраняются group_id/detected_at. Это явно выбранная цепочечная
трактовка для групп, суммарная длительность может превысить 60 минут.
Отдельные выезды и расход оборудования учитываются один раз обычным
планировщиком. При нехватке оборудования он добавляет RESTOCK.
Группа не обещает назначения всех её заявок: допуски/время могут мешать.

Карта показывает число автоматических переносов и групп, последние
изменения времени и количество заявок в каждой группе. Визуальная
приёмка браузера остаётся пользователю; синтаксис JS проверен.

Проверки: 15 Python-тестов, 5 API-тестов; Docker HTTP smoke подтвердил
загрузку, задержку, повторы, отклонение ошибки, прерывание, сохранение
автоматического слота и расширение группы с трёх до четырёх заявок.
Сценарий incident fixture использует искусственные pgp_relevant для
изолированной проверки связи, не заявляет реалистичность учебной аварии.

## Этап: перенос на следующие дни

После поиска в текущем дне система перебирает последующие даты до deadline.
Для принимающей даты использует сохранённые наряды, absent_staff_ids и план.
Проверяет новый двухчасовой слот полным планировщиком, включая дорожную
матрицу, квалификацию, оборудование, пополнение, обед, смену и возврат.
Существующие VISIT сохраняют исполнителя, arrival, start и end. При невозможности
такой вставки пробуется другой слот с шагом 30 минут, затем другая дата.
Дни, уже продвинутые событиями, автоматически не переписываются.
Если следующая дата не загружена, создаётся календарь со штатными сменами.
Сотрудники работают каждый загружаемый день согласно текущему OpenAPI;
производственный календарь выходных/праздников отдельно пока не задан.

Контрольный deadline не продлевается автоматически. Если до него нет
допустимого места или исчерпан бюджет поиска, наряд остаётся unassigned.
Отказ поиска не является доказательством математической невозможности.

Внутреннее поле _future_transfers содержит принимающие input/Plan.
Fastify валидирует их и атомарно переносит наряд из активного пула исходного
дня в принимающий. История переноса сохраняется в transferred_orders исходного
плана и журнале события. Двойного выполнения нет; существующие версии источника
не перезаписываются. В принимающем плане резервируется конкретное назначение.
Это расширение продуктового сценария, а не исходного правила H9 одного дня.

UI после события обновляет список дней, показывает дату переноса и позволяет
выбрать принимающий день. Сценарий NEXT-DAY CALENDAR PERSISTENCE PASSED
подтвердил PostgreSQL-сохранение, сохранность старой записи, выдачу UI и
идемпотентность повторной доставки. 17 Python-тестов и 5 API-тестов проходят.

При последующей ручной повторной загрузке дня через PUT исходный контракт
сбрасывает его план; такие загрузки могут заменить резервирование. Переносы
не являются защитой от явного сброса данных администратором.

## Актуализация перед публикацией main

Контрольный deadline теперь мягкий: не ограничивает подбор слота, исходное
значение сохраняется. Позднее окончание означает просрочку. Предыдущие
разделы документа об остановке поиска на deadline описывают старый этап.
Поиск будущих дат ограничен горизонтом 366 дней и вычислительным бюджетом;
универсальная гарантия назначения без подходящих ресурсов не реализована.
Изменение покрыто тестом test_overdue_order_still_receives_next_day_appointment.
Локальная форма и дамп остаются вне репозитория. Последняя проверка:
сборка TypeScript, 17 Python-тестов, 5 API-тестов, 4 теста модели UI прошли.
