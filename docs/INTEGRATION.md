# Интеграция Fastify, карты и планировщика

Ветка integration/fastify-map-planner собрана отдельной рабочей копией.
Это выборочный перенос компонентов, а не слияние всех файлов веток:

- Fastify, миграции, Compose: feat/official-rest-api, 8b8a905.
- web/, contracts/, данные и предложение БД: feature/dispatcher-app, 3b7b7bd.
- planner.py, planner_openapi.py, тесты и примеры: codex/planner-contract, df48777.

Старый FastAPI и экспериментальный OR-Tools-планировщик в сборку не включены.
Предложенная нормализованная схема Михаила сохранена, но автоматически
не применяется: пока сервер использует api_state и согласованный runner.

## Запуск

    docker compose up --build -d --wait

Адрес по умолчанию http://127.0.0.1:8080/. PostgreSQL 16 в именованном томе.
Локальный пароль по умолчанию предназначен только для оценки. Bash-скрипт
scripts/deploy.sh генерирует собственный .env. Миграции выполняются отдельно
перед API; planner — внутренний Python HTTP-сервис, порт не публикуется.

Для отдельной проверки на ноутбуке PowerShell:

    $env:API_PORT='18081'
    $env:DB_PORT='15436'
    docker compose -p dispatcher-integrated-qa up --build -d --wait

    python scripts/check_integrated.py --url http://127.0.0.1:18081 --allow-reset

Последняя команда заменяет данные целевого API. Использовать только тестовый
экземпляр. Она загружает небольшой пример Павла: сотрудники и три наряда,
строит план, передаёт задержку, проверяет новую версию, повтор и ошибку.
После неё в UI можно выбрать 2026-10-26 и посмотреть фактический план.

## Оставшиеся работы

- Новые продуктовые правила TEAM_DECISIONS.md: перенос прерванной работы,
  автоматическое согласование нового слота, группа аварии с визитами.
  Текущий smoke проверяет прежнюю семантику официального OpenAPI.
- Первичное выявление/расширение групп аварий: Python-адаптер пока только
  переносит уже существующие pgp_groups; автоматически новые не обнаруживает.
- Нормализованная схема БД и чтение без перезаписи общего JSON-снимка.
- Полный сценарий всех шести событий, независимая проверка H1–H10,
  визуальная проверка браузера, перезапуск с сохранением состояния.
- Начатый визит ровно на timestamp события: согласовать границу <=/<
  с адаптером, сейчас Павел замораживает только start < now.

Интеграционная ветка предназначена для совместной проверки. В main ничего
не вливается автоматически, работающий сервер не обновлялся.

## Этап: прерывание и временная недоступность

Реализовано: STAFF_UNAVAILABLE снимает текущий незавершённый визит с прежнего
исполнителя, сохраняя запись в day._interrupted_visits/Plan.interrupted_visits.
Наряд снова участвует в назначении вместе с последующими. Остаток длительности
считается как прежний прогнозный end минус timestamp события. Установленное
оборудование считаем оставшимся на объекте: оно остаётся расходом первоначального
мастера, повторного расхода на продолжение нет. Это явное допущение прототипа:
для реальных неустановленных/возвратных материалов нужна отдельная модель.

Временное выбытие: перед продолжением добавляется RESTOCK в домашнем СЦ,
не раньше until, с длительностью пополнения и заполнением до capacity.
Таким образом, until сейчас означает доступность для пополнения, а не готовность
немедленно выехать с уже пополненным комплектом. Запас не восстанавливается магически.

Отклонение от исходного H10 сделано только для прерванного текущего VISIT
при STAFF_UNAVAILABLE в соответствии с решением пользователя. Выполненные визиты
остаются замороженными. Исходный api_spec.yaml не изменён.

11 Python-тестов проходят, включая назначение остатка работы другому мастеру
и пополнение при возврате. В Docker повторно прошёл интеграционный smoke,
включая STAFF_UNAVAILABLE после задержки и выдачу истории прерывания через API.
История пока доступна в JSON, отдельное отображение её в интерфейсе не реализовано.

Если продолжение не укладывается в прежний слот, оно пока попадает в unassigned.
Автоматическое изменение слота и группа аварии с индивидуальными визитами —
следующий этап; этот коммит не объявляет их завершёнными.
