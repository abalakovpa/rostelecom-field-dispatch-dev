# Переход на официальный REST API

Источник внешних форматов — ../api_spec.yaml (OpenAPI 3.0.3, версия 1.0.0).
HTML-представление организаторов: api_spec.html. Файлы сохранены без изменений.
Черновик planner-contract.md описывает прежний внутренний интерфейс и не
заменяет официальный контракт. Код планировщика остаётся в PR № 4 Павла.

## Состояние реализации

Сейчас сервер Fastify реализует только GET /health и подключение PostgreSQL.
Официальный API /api/v1 пока не реализован. Текущий порт — 3000;
спецификация ожидает по умолчанию 8080. Наличие спецификации в git не означает
готовности сервера к внешней оценке.

## Порядок реализации

1. Зарегистрировать схемы Fastify по OpenAPI с учётом nullable, allOf и oneOf.
   Проверять запросы и ответы, игнорировать неизвестные входные поля согласно
   соглашениям спецификации. Лимит тела — 100 МБ.
2. Добавить /api/v1/health, PUT /api/v1/reference и
   PUT /api/v1/reference/travel-matrix, затем PUT /api/v1/days/{date}.
3. Согласовать с Павлом секунды переездов, latest_start, окно перерыва,
   пополнение до equipment_capacity и правила заморозки начатых остановок.
4. Добавить POST и GET /api/v1/days/{date}/plan с официальным Plan,
   версиями и модельным временем. Планировщик вызывается сервером.
5. Добавить POST /api/v1/days/{date}/events: NEW_ORDER, ORDER_CANCELLED,
   VISIT_DELAYED, ORDER_TRANSFERRED, STAFF_UNAVAILABLE, TIME_TICK.
6. Обеспечить атомарность изменения состояния, идемпотентность event_id,
   контроль порядка событий и сохранение начатых остановок.
7. Проверить полный сценарий организаторов и лимиты 300 с / 10 с.

## Уточнения для планировщика

- travel_matrix.durations_sec — секунды без округления до минут;
  базовая оценка не применяет hourly_factors.
- latest_start и deadline приходят во входном наряде.
- BREAK — в точке предыдущей остановки, без переезда к перерыву.
- RESTOCK доводит остаток до equipment_capacity.
- Расход оборудования происходит на старте визита и не повторяется
  при пересчёте. VISIT_DELAYED.expected_end определяет новый прогноз окончания.
- STAFF_UNAVAILABLE.until задаёт конец недоступности; после него сотрудник
  продолжает смену из своего СЦ.
- ПГП: не менее 3 релевантных нарядов одного узла за 60 минут;
  уже начатые визиты остаются в маршруте и в группу не включаются.

Все перечисленные работы запланированы, но в этом коммите не реализуются.
