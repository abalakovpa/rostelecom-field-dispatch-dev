# Границы интеграции

| Участник | Рабочая зона |
|---|---|
| Серверный разработчик | Fastify, официальный REST API, Docker, общий запуск миграций и развёртывание |
| Павел | Итоговый планировщик и перепланирование |
| Наша часть | `web/`, UI-контракт и предложение схемы БД |

На согласование подготовлены `contracts/ui-api.yaml`, JSON-примеры,
`docs/ui_api.md`, `db/proposals/001_dispatch_schema.sql` и `db/README.md`.
Эти предложения ещё не приняты другим разработчиком: подключать их автоматически
к работающей базе или менять общую инфраструктуру нельзя.

Прежний Python API, экспериментальный планировщик, их зависимости, Docker и тесты
вынесены в `demo/`. Общих `compose.yaml`, `.env.example` и установщика в этом наборе
нет. Рабочие файлы команды должны остаться из её ветки. Демо-конфигурации явно
отделены и используют PostgreSQL 16. Полезные части старого планировщика перечислены
в `demo/README.md`; решение о переносе принимает Павел.

## Порядок дальнейшей работы

1. Серверный разработчик согласует три GET UI и DTO; карта подключается к его Fastify.
2. Сверяем SQL с уже существующей PostgreSQL 16 и оформляем разностные миграции
   в командном runner. Тестируем чистую базу и обновление существующей.
3. С Павлом сравниваем проверки ограничений и формат предупреждений. Убираем
   дублирующий алгоритм из итоговой сборки, сохраняя только согласованные части.
4. Проверяем общий запуск и сценарий «загрузка → план → событие → новая версия».
5. После ревью готовим ограниченный PR карты/БД. Старая ветка целиком не сливается.

Изменения подготовлены для публикации в `feature/dispatcher-app`; перед отправкой
сохранена отдельная локальная резервная копия всех веток GitHub и истории Git.
Кэши исключены из текущего набора файлов, но остаются в истории прежнего коммита:
историю Git не переписываем. Вопрос обеда оставлен отложенным в `open_questions.md`;
поведение прототипа не менялось. Отчёт `local_integration_validation.json` фиксирует
локальные проверки до публикации, а не совместный запуск командного приложения.
