# Оборудование мастера и пополнение в СЦ

В принятой модели инвентарь — ONT, ROUTER и STB. Профиль, технологии и допуск
к высоте проверяются отдельно. Произвольные инструменты/запчасти вне этих
трёх типов спецификация организатора не описывает.

У сотрудника есть equipment_start — комплект в начале каждой смены,
equipment_capacity — комплект после пополнения. У наряда required_equipment —
его расход. Остатки считаются по маршруту. Расход происходит в начале визита,
как требует H7 api_spec.yaml; это не отметка фактической установки от мастера.

Если во время текущего визита поступила новая заявка:

1. Уже начатый визит сохраняется, его оборудование уже списано один раз.
2. Планировщик пробует вставить новый визит после текущего и среди дальнейших
   остановок с учётом слота, допуска, дороги, обеда, смены и остатка комплекта.
3. Если остатка достаточно, специально ехать за пополнением не требуется.
4. Если недостаточно, но заявка помещается в equipment_capacity, подбирается
   остановка RESTOCK в открытом СЦ. Учитываются оба участка дороги и время
   пополнения. Кандидаты сравниваются по началу работ, при равенстве — по сумме
   дороги и времени пополнения. Это локальный выбор маршрута, не доказательство
   глобально оптимального решения для всего календаря.
5. После RESTOCK комплект становится equipment_capacity, затем списывается
   расход новой заявки. Если требуется больше вместимости, пополнение не поможет:
   нужен другой совместимый мастер или обоснованная причина неназначения.
6. При невозможности выполнить в допустимое время включается действующая
   политика поиска другого слота/дня. Требование оборудования не обходится.

По H8 пополнение разрешено в ЛЮБОМ открытом СЦ; старт и финиш смены —
в закреплённом СЦ. Поэтому пополнение может быть в другом центре, если это
позволяет раньше попасть на заявку. По H7 пополнение доводит комплект до
equipment_capacity, а не до вручную выбранного количества только на один визит.
Запасы самих СЦ считаются доступными: остатков склада по отдельным СЦ в
спецификации нет. Автоматический выбор не гарантирует того же мастера: он
выбирает допустимое назначение; тестовое закрепление позволяет проверить
продолжение маршрута конкретного сотрудника.

## Проверка в режиме отладки

Выберите новую дату и блок «Оборудование сотрудников».
Для нужного мастера задайте ONT/ROUTER/STB и сохраните стартовый комплект.
Значения не должны превышать вместимость. Это настройка конкретного дня:
общие справочники и другие даты не меняются. Заявки и события закрывают
редактирование старта смены. Остаток нельзя исправлять посреди маршрута,
подменяя историю расхода; штатный способ пополнения — RESTOCK.

В обычной форме создания теперь есть «Оборудование для этой заявки».
При изменении адреса восстанавливается прежний шаблон: ROUTER=1,
ONT=1 для PON, STB=0. Затем количества можно изменить вручную.
Список подходящих мастеров проверяет вместимость по введённому комплекту.
Текущее отсутствие оборудования не исключает сотрудника: система может
спланировать пополнение. Генератор нагрузки сохраняет прежний шаблон расхода.

В отладке есть таблица всех сотрудников: старт, остаток на model_now,
вместимость и запланированные пополнения с адресацией по ID СЦ.
Текущий остаток учитывает визиты с start <= model_now и пополнения только
после RESTOCK.end. Во время загрузки в СЦ новый комплект ещё не доступен.
На карте в списке «Команда» карточки также показывают остатки. В маршруте
остановки RESTOCK видны на Ганте; equipment_after содержит баланс после
каждой остановки, в том числе будущий, и не равен текущему остатку мастера.

Сценарий без возвращения: задайте ROUTER=2, создайте закреплённую заявку
с расходом ROUTER=1. Переведите время внутрь визита (начало + одна минута).
Остаток должен стать 1. Создайте второй наряд с расходом ROUTER=1 на следующий
слот тому же сотруднику. Между визитами RESTOCK не нужен.

Сценарий с пополнением: повторите на другой новой дате с ROUTER=1 на старте.
Во время первого визита остаток уже 0. Второй наряд должен получить RESTOCK
перед своим VISIT, если время позволяет, либо допустимый перенос. Уже начатый
первый визит не меняет время и адрес. На обеих датах проверьте, что остатки
никогда не отрицательные и оборудование не списывается дважды при пересчёте.

## Границы интеграции

Официальные equipment_start/capacity/required_equipment остаются в прежнем
формате. Настройка тестовой смены — расширение входа планировщика
day._equipment_start_by_staff. Оно применяется только к этому дню, а будущие
дни используют свои настройки или стандартный комплект из справочников.
Fastify использует тот же старт для расчёта equipment_after и отклоняет
неизвестных мастеров, отрицательные/дробные значения и превышение вместимости.

GET /api/ui/days/{date}/inventory возвращает editable, model_now, staff[] с
initial/current/capacity/restocks. POST по тому же адресу принимает
{"staff_id":"ST-001","equipment_start":{"ONT":0,"ROUTER":2,"STB":0}}.
При первом сохранении создаётся пустой тестовый день. Повторное редактирование
после заявок/событий возвращает 409. Стандартный OpenAPI не менялся.
В ответ /api/ui/days/{date} добавлена inventory для карточек команды.

Проверено в отдельном Docker через реальные Fastify, PostgreSQL и планировщик:
заявка во время визита при старте ROUTER=1 добавляет RESTOCK, а при ROUTER=2
едет напрямую; в обоих случаях сохранены начало/окончание текущего визита,
два назначения и неотрицательные остатки. В Chrome проверены настройка
старта, расход ROUTER=2 в HTTP-заявке и закрытие настройки после создания.
Прошли 39 Python-, 23 JS- и 11 API-тестов, а также сборка TypeScript.
