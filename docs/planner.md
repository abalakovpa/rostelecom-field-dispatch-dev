# Первоначальный расчёт смены

Реализован `POST /api/v1/days/{date}/plan` с `time_limit_sec` от 1 до 300.
Кнопка карты использует 30 секунд. Результат сохраняется в PostgreSQL как версия 1;
в деморежиме хранится в памяти до перезапуска. Повторный расчёт до событий заменяет
первую версию. При наличии событий или параллельном расчёте того же дня — 409.

Алгоритм — эвристическое построение маршрутов с выбором назначений через OR-Tools
CP-SAT. Для каждого сотрудника и доступного наряда строится кандидат полного
маршрута: выезд, визиты, один обед, пополнение при необходимости и возврат.
Варианты положения обеда перебираются между визитами. CP-SAT выбирает пакет
непересекающихся назначений (один наряд и сотрудник в пакете не повторяются).
Повторы имеют вес 2; время проезда и длина очереди — вторичные критерии.
Далее строится следующий пакет, пока есть допустимые вставки и время.

Это ограниченная эвристика: она пробует вставить новый визит в каждый промежуток
существующей очереди, но не выполняет глобальные обмены и не гарантирует оптимальный VRPTW.
Выбор СЦ для пополнения жадный. При исчерпании поиска для подходящего наряда
используется причина OTHER с явным пояснением, что невозможность назначения
не доказана. Точная лексикографическая оптимизация всех целей кейса ещё впереди.

Перед сохранением независимая проверка проигрывает маршруты и подтверждает:
профили/технологии/высоту; смены; норматив и срок; слот; дорогу по матрице;
ровно один обед на используемый маршрут; расход и пополнение АО; часы СЦ;
возврат в свой СЦ; единственный учёт каждого наряда. Недопустимый план не сохраняется.
Условия H10 между версиями теперь проверяются при событиях, см. `events.md`.

Начальная ПГП обнаруживается по регистрации трёх релевантных нарядов одного узла
за 60 минут без чтения `fact`. Они исключаются из индивидуальных визитов и
возвращаются в `pgp_groups`. События и предупреждения при снятии/передаче визита
добавлены отдельно. Прогноз оставшейся очереди до ремонта, своевременность
предупреждений и допустимые рекомендации описаны в `risks.md`.

После расчёта список показывает исполнителя, номер визита и начало. Выберите
сотрудника в поле маршрута — карта запросит дорожную GeoJSON-линию OSRM и
покажет нумерацию визитов. Время расчёта и проверки всегда берётся из загруженной
матрицы; геометрия OSRM служит только отображению. При недоступности OSRM
прямые линии не подставляются; план остаётся доступным со списком назначений.
Публичный сервис используется через HTTP для синтетических координат, ответ
кэшируется в памяти по координатам. Локальный OSRM и его конфигурация — следующий
инфраструктурный этап. Геометрия может быть от более свежей дорожной сети,
чем загруженная матрица, и не определяет допустимость расписания.

Код: `planner/solver.py`, независимый проверяющий — `planner/validate.py`.
Docker копирует модуль планировщика; зависимости входят в `requirements.txt`.
Полная загрузка данных по API организаторов, Гант и полноценная проверка
производительности на скрытом наборе остаются в плане работ.

Первый живой прогон на 12 октября: 235 визитов из 350 нарядов, 3 наряда ПГП,
112 неназначенных, около 20 секунд. План сохранён и прочитан обратно из PostgreSQL,
ответ проверен по исходной схеме Plan OpenAPI. Для ST-001 получена дорожная линия
OSRM из 615 вершин, в браузере проверены линия и шесть пронумерованных визитов.
Это один замер на собственном наборе, а не гарантия времени или качества на всех
днях и скрытом наборе. Отчёт — `data/planner_validation_report.json`.
