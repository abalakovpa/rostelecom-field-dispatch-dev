# Серверная часть: объяснение для команды и защиты

Статус на 14 ноября 2026 года. Проверены исходный PDF кейса, api_spec.yaml,
локальная ветка feat/official-rest-api и ранее предоставленные логи сервера.
Это отчёт о текущей работе, а не заявление о завершении всего кейса.

## 1. Моя ответственность

Я разрабатываю серверную часть: REST API на Fastify/TypeScript, приём и
проверку данных, хранение состояния смены, передачу данных планировщику,
сохранение результатов, Docker Compose и сценарий развёртывания.

В PDF это прежде всего основное задание 5 (REST API) и задание 7
(контейнеризация и документация), а также серверная поддержка задания 3
(перепланирование). Алгоритм оптимизации делает Павел; карта и модель БД
согласуются с Михаилом. Наличие маршрута /events ещё не означает, что
полностью реализованы оптимизация, ранние предупреждения и выявление ПГП.

В PDF, раздел 3, перечислены Python/Go/Java. Fastify работает на Node.js:
это выбранная пользователем архитектура команды, а не технология из этого
перечня. Необходимо уточнить у организаторов допустимость Node.js для
внешнего API при Python-планировщике. Не утверждать, что PDF требует Fastify.

## 2. Что уже подтверждено

На сервере Ubuntu 26.04 развёрнут первоначальный инфраструктурный каркас:
PostgreSQL 16, миграция 001_state.sql и Fastify endpoint /health.
Предоставленные серверные логи показывают db Healthy, api Healthy,
ответ status=ok, db=ok. Через pgAdmin пользователь увидел таблицы
schema_migrations, dispatch_snapshots, dispatch_plans, dispatch_events.
Это подтверждает запуск, соединение и применение первой миграции;
предметные данные и рабочий план этим не проверяются.

Локально добавлен официальный HTTP-слой /api/v1, миграция 002_api_state.sql,
валидация OpenAPI, транзакционное сохранение состояния и интерфейс расчёта.
На момент отчёта эти изменения находятся в незакоммиченной рабочей копии
ветки feat/official-rest-api, не подтверждены на сервере.

Повторно выполнены сборка TypeScript и три автоматических HTTP-сценария.
Все прошли. В тестах используется memory-store с копированием состояния
перед операцией и подставной планировщик. Это не доказательство корректности
PostgreSQL-транзакций в реальном окружении или алгоритма планирования.

## 3. Как устроен сервер

api/src/index.ts — точка входа. Создаёт приложение, начинает слушать порт
на 0.0.0.0 внутри контейнера, обрабатывает остановку и закрывает пул БД.
0.0.0.0 позволяет обращаться к сервису через Docker-сеть.

api/src/app.ts — сборка Fastify, лимит тела 100 МБ, requestTimeout 330 с,
регистрация маршрутов и общий формат ошибок. Отдельная buildApp позволяет
проверять HTTP без открытия реального порта через app.inject.
requestTimeout сам по себе не является жёстким ограничителем всей
длительности обработчика и расчёта: общий бюджет ещё нужно проверить.

api/src/openapi.ts — читает api/spec/api_spec.yaml, получает схемы и
преобразует OpenAPI nullable в JSON Schema anyOf с null. Локальные ссылки
переписываются в идентификаторы urn:dispatch:... для регистрации в AJV.
Описания и примеры не участвуют в проверке. Форматы дат проверяются AJV.
Файл api/spec/api_spec.yaml сейчас копирует корневой api_spec.yaml:
нужна автоматическая проверка их совпадения, чтобы копии не разошлись.

api/src/official-api.ts — маршруты, проверки связей данных и сценариев,
вызов планировщика, проверка его ответа, версии и журнал событий.
Схема проверяет форму данных; отдельные функции проверяют смысл и ссылки.

api/src/store.ts — слой хранения. PostgresStore внутри транзакции читает
api_state.document через SELECT ... FOR UPDATE, вызывает обработчик,
записывает JSON и подтверждает транзакцию. При исключении запись не сохраняется.

api/src/db.ts — пул PostgreSQL и withTransaction: BEGIN, выполнение
операции, COMMIT; при ошибке ROLLBACK; finally освобождает соединение.
Параметры запросов передаются отдельно от SQL, а не склеиваются со входом.

api/src/planning.ts — интерфейс Planner и HTTP-клиент к PLANNER_URL.
Сейчас это предложенный интерфейс, не подключение к готовому коду Павла.

## 4. Семь официальных операций

GET /api/v1/health — обращается к хранилищу; возвращает готовность, если
новая таблица состояния доступна. Старый /health проверяет SELECT 1.
Наличие status=ok не доказывает готовность планировщика.

PUT /api/v1/reference — принимает справочники. Проверяет дубликаты ID,
существование СЦ для сотрудников и домов, начальное оборудование против
вместимости. Если матрица уже есть, проверяет покрытие точек. После
успешной загрузки заменяет справочники и очищает дни, планы и события.

PUT /api/v1/reference/travel-matrix — проверяет обе матрицы N×N,
нулевую диагональ и наличие всех точек справочников, если они загружены.
Значения времени остаются в секундах. Симметрия не требуется.

PUT /api/v1/days/{date} — проверяет совпадение даты пути и тела,
уникальность нарядов, типы работ, принадлежность дома узлу, отсутствие
регистраций из будущего, временные окна и отсутствующих сотрудников.
Повторная загрузка сбрасывает план и события именно этого дня.

POST /api/v1/days/{date}/plan — требует день и матрицу, вызывает расчёт,
формирует версию 1. До событий разрешает повторный первоначальный расчёт,
после принятого события возвращает 409.

GET /api/v1/days/{date}/plan — возвращает сохранённую версию; если день
или план отсутствуют, возвращает 404. Сам ничего не рассчитывает.

POST /api/v1/days/{date}/events — проверяет схему и существование плана.
Сначала ищет уже принятый event_id: возвращает duplicate=true с прежней
версией. Затем проверяет порядок timestamp. Равное время допускается.
После успешного расчёта сохраняет состояние, план и ответ на событие вместе.

## 5. Как проходит событие

1. Fastify проверяет JSON по Event, включающей шесть вариантов события.
2. Хранилище блокирует снимок, чтобы два изменения не перезаписали друг друга.
3. Проверяются ссылки на наряд/сотрудника и применимость события.
4. NEW_ORDER добавляет наряд. Модельное время становится timestamp события;
   событие добавляется в журнал рабочего снимка.
5. Планировщику передаётся {reference, matrix, day, previous_plan, event}.
6. После ответа сервер выставляет дату, as_of, based_on_event_id и версию.
7. Проверяются схема Plan, однократный учёт всех нарядов и неизменность
   начатых остановок, кроме разрешённого изменения конца текущего визита.
8. Сохраняются новый план и EventResult. При ошибке операция откатывается.

Для VISIT_DELAYED проверяется, что визит уже идёт, а expected_end позже
прежнего окончания. Для ORDER_TRANSFERRED проверяется actual_end внутри
допустимого интервала. Для STAFF_UNAVAILABLE проверяется until.
Перестройка маршрутов, применение отмены, исключение недоступного
сотрудника, расчёт оборудования и предупреждений остаются обязанностью
ещё не подключённого адаптера расчёта. Нельзя говорить, что они уже
реализованы серверным кодом целиком.

Модельное время берётся из day.now и timestamp событий. performance.now
используется для измерения длительности вычисления, не для времени смены.
При отсутствии PLANNER_URL ответ — 503 PLANNER_UNAVAILABLE. Это явная
ошибка зависимости, успешный план не подставляется.

## 6. Ошибки и гарантии

400 — неверная структура JSON или схема; 422 — несогласованные данные;
409 — нарушен порядок вызовов/событий; 404 — нет дня или плана;
502 — недопустимый ответ планировщика; 503 — расчёт недоступен.
Подробности неожиданных ошибок пишутся в серверный лог; наружу — общий 500.

Идемпотентность означает: повтор event_id не создаёт новую версию.
Транзакционность означает: ошибка внутри операции не оставляет половину
изменений в PostgreSQL. Она не гарантирует внешние эффекты удалённого
планировщика, если он их делает: расчёт должен быть без таких эффектов.

## 7. Docker и запуск

Compose поднимает БД, ждёт её healthcheck, запускает одноразовый migrate,
после успешного завершения — API. Мигратор хранит имена применённых SQL
в schema_migrations, выполняет каждый новый файл в транзакции и защищается
advisory-lock от параллельного запуска. BOM перед SQL удаляется загрузчиком:
это исправление реальной ошибки первого серверного запуска.

Данные PostgreSQL хранятся в именованном томе. Пересоздание контейнера
не равно удалению данных; down -v том удаляет. Новые миграции добавляются
новыми файлами, уже применённые изменять нельзя.

Bash-скрипт поддерживает установку Docker на Ubuntu 24.04/26.04, генерирует
пароль при отсутствии .env, ограничивает права файла и ждёт готовности
сервисов. Публичные порты БД/API привязаны к 127.0.0.1 хоста.
Доступ с ноутбука организован SSH-туннелем; секреты не коммитятся.
Локальный официальный API использует 8080; ранее поднятый стенд — 3000.
Существующий .env автоматически не переписывается, порт при обновлении
нужно проверить.

## 8. Что проверяющий обоснованно может спросить

- Почему много any? Типизация предметных объектов пока не доведена до
  строгих TypeScript-интерфейсов. Runtime-проверка есть, но any снижает
  надёжность внутренних преобразований. Это задача доработки.
- Вы проверяете все H1–H10? Нет. Сервер проверяет схему, учёт и часть
  заморозки; полный независимый валидатор маршрута ещё нужен.
- Почему весь снимок в JSONB? Быстрый способ согласовать атомарный прототип.
  Чтение даже GET сейчас блокирует и перезаписывает общий снимок с матрицей;
  это узкое место и требует разделения данных/чтения и согласования с Михаилом.
- Выполняется лимит 10 с? Пока не доказано. Таймаут HTTP к расчёту 9 с не
  включает ожидание SQL-блокировки, валидацию и COMMIT. Нет общего дедлайна.
- Достаточно ли трёх тестов? Для готовности всего сервиса — нет. Они проверяют
  версии, дубли, порядок, откат при падении расчёта и часть неверных входов.
- Все ли события работают? Схемы принимают все шесть, но полные последствия
  требуют интеграции и отдельных сценариев каждого типа.
- Даты корректны при любом UTC-смещении? Текущая проверка дня через slice
  требует исправления на сравнение в часовом поясе смены.
- Можно ли безопасно обновлять матрицу после расчёта? Политика снимков матрицы
  для уже загруженных дней пока не реализована, требует согласования.
- Неизвестные поля всегда игнорируются? Fastify настроен removeAdditional;
  сочетания oneOf/allOf и поля вроде fact требуют дополнительных тестов.
- Подключены ли карта и Python? Пока нет. Нужны UI-эндпоинты, адаптер и
  единое согласованное хранилище. Альтернативные ветки не считаются интеграцией.
- Что с нагрузкой? 350–450 нарядов, 300 с на день и 10 с на событие ещё
  не проверены на полном стеке. Не приводить результаты тестов HTTP-слоя
  как измерение производительности решения.
