# Предложение схемы для согласования с серверным разработчиком

Целевая версия команды — PostgreSQL **16**. Переход на 17 не требуется.
SQL из `proposals/` — предложение, **не активная миграция общего приложения**.
Ни одна миграция в рамках этой корректировки к существующей БД не применялась.

`proposals/001_dispatch_schema.sql` содержит исходную схему прототипа. Она создаёт
`dispatch`, домены, справочники, дома/узлы, матрицы, дни, наряды, события и планы.
SQL транзакционный (`BEGIN/COMMIT`), рассчитан на ещё отсутствующую схему; повторный
запуск не является способом обновления существующих таблиц. В файле не используются
специальные возможности PostgreSQL 17; реальный прогон на командной PostgreSQL 16
ещё не выполнен. Старые отчёты относятся к другой тестовой версии PostgreSQL.

## Что согласовать до подключения

- Имя схемы, владельца, совпадения таблиц/доменов с существующими миграциями.
- Серверные сущности `planning_days`, `plans`, `events`: состав столбцов,
  хранение текущего состояния и история, внутренний контракт с Павлом.
- Нужны ли `training_orders` и JSON-снимки справочников/дней в общей схеме.
- Реестр версий миграций: `dispatch.schema_migrations` в предложении — старый
  механизм прототипа, он не должен конкурировать с реестром Fastify-проекта.
- Порядок создания FK и ограничения, которые уже проверяются сервером/планировщиком.

Основные таблицы справочников: `service_centers`, `staff`, `buildings`,
`access_nodes`, `access_node_buildings`, `work_types`. DTO карты не обязаны
совпадать с именами SQL-столбцов: Fastify собирает ответы по `contracts/ui-api.yaml`.

## Подключение к командному запуску миграций

1. Серверный разработчик сравнивает предложение с уже применённой схемой.
2. Для пустой базы согласованную схему оформляем миграцией в его реестре;
   из SQL исключаем собственные `BEGIN/COMMIT` и `schema_migrations`, если
   транзакциями и версиями управляет общий runner.
3. Для существующей базы делаем **новую** миграцию `ALTER/CREATE` по фактической
   разнице, а не повторяем исходный `CREATE SCHEMA` и не меняем старую миграцию.
4. Проверяем два пути на PostgreSQL 16: чистая база и обновление с существующими
   данными, затем повторный запуск без повторного применения. При сбое — откат.
5. Приложение стартует после успешного отдельного запуска миграций.

`/docker-entrypoint-initdb.d` срабатывает только при первичной инициализации тома
и не заменяет эти шаги. Общие Compose, переменные и установщик сюда не добавляются.
FastAPI-таблица `dataset_state` из `demo/db/migrations/002_dataset_state.sql`
в общую миграцию не предлагается без отдельного согласования.
