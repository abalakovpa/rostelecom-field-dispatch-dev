## Запуск в PowerShell

Нужен запущенный Docker Desktop с Linux-контейнерами.

```powershell
Copy-Item .env.example .env
```

Укажите собственный `POSTGRES_PASSWORD` в `.env`, затем:

```powershell
docker compose up -d db
docker compose ps
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "TABLE dispatch.schema_migrations;"'
```

При первом запуске на пустом томе Docker автоматически применяет миграцию.
Контейнерная БД доступна на `localhost:5434`, имя/пользователь — из `.env`, схема — `dispatch`.
Из другого контейнера того же Compose адрес будет `db:5432`.
Сервис `db` — база; сервис `api` в Compose — FastAPI с картой и первоначальным
планировщиком OR-Tools. Для всей связки используйте `docker compose up --build -d`.
Для изменения внешнего порта контейнера задайте другой `DOCKER_POSTGRES_PORT`
для контейнерной БД. Это отдельная база, не заполненная вами установка из pgAdmin.

Данные сохраняются в томе `postgres_data`. Повторный запуск контейнера не
применяет изменённую миграцию. После первого применения эту миграцию не редактируют:
новые изменения оформляют отдельными файлами `002_*.sql` и применяют через `psql`
с `ON_ERROR_STOP=1`. Не удаляйте том ради обновления схемы.

## Что подготовлено и что дальше

Сгенерирован собственный набор разработки: 5 СЦ, 40 сотрудников (28 LTP3/12 INSTALL),
20 узлов, 80 домов, 3500 нарядов за 10 рабочих дней и сценарий событий. Матрица
проезда рассчитана по дорожной сети OSRM, источник закэширован для воспроизводимости.
Это синтетические данные команды, а не официальный скрытый набор организаторов.
Все исходные файлы описаны в `data/README.md` и проверяются `scripts/validate_data.py`.
Добавлены чтение данных через API, карта, первоначальный расчёт OR-Tools,
независимая проверка плана, его сохранение и дорожное отображение выбранного
маршрута. Подробности и ограничения — `docs/planner.md`. Добавлены события и
перепланирование с заморозкой истории, идемпотентностью и транзакциями (`docs/events.md`).
Известное противоречие кейса, которое нужно напомнить при финальной сверке,
зафиксировано в `docs/open_questions.md`. Следующий этап — полная загрузка данных
через API, улучшение качества, предупреждений и интерфейса.

В pgAdmin после миграции откройте `db/seeds/001_generated_data.sql` в Query Tool
и выполните F5. Импорт требует пустых таблиц и не заменяет существующие записи.
Миграция и весь SQL-экспорт успешно выполнены на встроенном PostgreSQL 18.6
(PGlite); результат — `data/database_validation_report.json`. Подключение к
вашему PostgreSQL через pgAdmin и запуск Docker отдельно ещё не проверены.

Схема не требует PostGIS: координаты используются для карты и OSRM, а оценка
проезда идёт по единой матрице. Физические часы БД используются только для
служебной даты применения миграции; бизнес-время приходит из `now` и событий.

## Проверка запуска без .env

Для локальной оценки из чистой копии достаточно:

    docker compose up --build -d

Адрес: http://127.0.0.1:8080/api/v1/health, интерфейс: http://127.0.0.1:8080/.
По умолчанию используется локальный пароль local-evaluation-only; это
публичная конфигурация для проверки, не секрет. Порты привязаны к localhost.
Для серверного развёртывания задать собственный POSTGRES_PASSWORD через .env.
При смене пароля существующий том не меняет пароль пользователя автоматически.
Не удалять том для исправления пароля: менять пароль в БД согласованно.

Время первой сборки зависит от загрузки образов и Python-зависимостей.
В текущем Dockerfile зависимости скачиваются; полностью автономная сборка
без подготовленных образов не обеспечена. Требование готовности за 120 с
проверяется отдельно, не подменяется временем всего скачивания.
